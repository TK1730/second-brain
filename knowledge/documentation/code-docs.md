# コードを説明する文書の書き方

機能やライブラリを説明する文書の考え方をまとめる。
目的は、そのコードを初めて見る人が、コードを開く前に「どう振る舞うか」と「どこから読めばよいか」を理解できることである。
内容は Google の docguide の Documentation Best Practices と Diátaxis の Explanation の考え方をもとにしている。

## 書く場所の分担

関数ごとの約束はコメントに、振る舞いの詳細はテストに任せ、docs には複数のファイルにまたがる全体像と「なぜ」だけを書く。
どこに何を書くかの考え方は [書く場所の選び方](/knowledge/documentation/where-to-document.md) を参照する。

docs には次のものを書かない。必要なら、正とする場所へリンクする。

- 関数のシグネチャ、引数と戻り値の一覧、型定義の写し。
- 網羅的なテストケースの一覧。
- 実装コードの抜粋。仕組みの説明に必要な場合は、擬似コードか図にする。

## コードを説明する文書の骨子

[文書の構成](/knowledge/documentation/document-structure.md) の骨子を、機能を説明する文書に当てはめると次のようになる。
各見出しの `<対象>` には機能名やライブラリ名を入れる。当てはまる内容が無い節は省く。

```markdown
# <対象>

<対象> が何をするものかを 1〜3 文で書く。

## <対象> でできること・できないこと

## <対象> の用語

## <対象> の構成と読む順番

## <対象> の振る舞い

## 決定理由 (Rationale)

## See also
```

- できること・できないこと: 使う人から見た振る舞いを箇条書きで書く。内部の仕組みではなく、外から観察できる結果と、対象外にしたことを書く。
- 用語: 文書とコードで使う言葉を、表示名・コード上の識別子・説明の表にする。コード上の識別子を併記すると、読者がコードを全文検索できる。
- 構成と読む順番: 関わるファイルを、読むべき順に番号付きリストで並べる。各項目には、そのファイルが負う責務と負わない責務を 1〜2 文で書く。パッケージが 3 つ以上あるときは、リストの前にコンポーネント図を置き、呼び出しの向きを矢印で示す。
- 振る舞い: 次の中から対象に合うものを選んで書く。
  - 全体の流れ: 利用者の操作から結果までを、シーケンス図で書く。
  - 状態遷移: 状態を持つものは、状態遷移図で書く。状態を変えない参照系の操作には描かない。
  - 入力と結果の具体例: 全体像の理解に必要な代表例と境界値に絞って表や入出力例で示す。網羅的な一覧はテストに任せる。
  - 注意点: 複数のファイルにまたがる注意点だけを書く。1 つの関数で閉じる注意点はテストに書く。

## 機能が大きいときの分け方

1 つの機能に操作が 3 つ以上あり、1 つの文書では読みにくいときは、ディレクトリを分けて概要の文書と操作ごとの文書に分割する。

| 文書 | 書くこと |
| :--- | :--- |
| 概要 (`overview.md`) | できること・できないこと、用語、操作を比べる表、コンポーネント図と読む順番、機能全体に関わる決定理由 |
| 操作ごとの文書 | 結果の表、入出力の例、シーケンス図、状態が変わるなら状態遷移図、注意点、その操作だけに関わる決定理由 |

操作ごとの文書は、時間が経ってから仕様を振り返る人が最初に開く文書である。
その文書だけで「何を送ると何が返るか」と「なぜそうしたか」が分かるようにする。

## 振る舞いを正確に書く

- 読者は書かれたとおりに信じるので、振る舞いは誇張せずに書く。
- 「完全に」「誤差ゼロ」のような言い切りを避け、実際の挙動と限界を書く。
- 分からないことは推測で書かず、コードかテストで確かめてから書く。

## レビュー観点

レビューでは、次の問いに文書だけで答えられるかを確かめる。

1. このコードは何のためにあり、何をしないか。
1. 最初に開くべきファイルはどれか。
1. 代表的な操作をしたとき、どの順で何が呼ばれ、何が保存されるか。
1. 境界値や異常な入力のとき、どうなるか。
1. 呼んでいる API の仕様と、その API が使うテーブルへ辿れるか。
1. 時間が経ってから振り返る人が、操作ごとの文書だけで、何を送ると何が返るかと、なぜそうしたかに答えられるか。

## 決定理由 (Rationale)

- 関数ごとの約束をコメントに、振る舞いの詳細をテストに置き、docs を全体像と「なぜ」に絞るのは、コードと文書の二重管理による陳腐化を防ぐためである。
- 操作が 3 つ以上ある機能をディレクトリで分割するのは、1 つの文書に複数の操作の説明や図が混ざると、初めて読む人がどの話がどの操作のものか判別しにくくなるためである。
