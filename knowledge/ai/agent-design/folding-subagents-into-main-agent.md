# サブエージェントをメインのエージェントループへ統合する判断と手順

サブエージェントを減らし、1 つのエージェントにスキルとツールを持たせる設計の判断基準と手順をまとめる。
内容は Anthropic の記事「Building agents: When to fold subagents into your main agent loop」（2026-10-22 公開、著者 Diane Sarkis）[^claude-article] の要約である。
数値は、記事が紹介する個別の事例と Anthropic 自身の経験であり、一般化した測定ではない。

## 基本の考え方

- 複数のエンタープライズ導入で、スキルを持つ単一のエージェントが、単一プロンプトの設計やサブエージェント設計より高品質になることが多く、1 タスクあたりのコストと遅延も下がることが多かったと記事は述べる。
- 大きな組織は、組織図に似たマルチエージェントを作りがちである。その結果、文脈の欠落、サブエージェントの乱立、システムプロンプトの矛盾、局所的な評価、遅延の増加が起きる。
- 新しいモデルは 1 つのループでより多くを扱えるため、判断の一部をハーネスからモデルへ移せる。

## サブエージェントを残す条件

- 文脈の肥大で、単一ループの性能が測定できる形で落ちている。
- 新しい文脈で並列に走らせ、終われば捨てられるタスクがある。
- ツール選択がうまくいかない、またはシステムプロンプトに矛盾する指示がある。

分割は、問題の種類ではなく文脈で決める。独立した調査の経路、インターフェースが明確な部品、ブラックボックスの検証が向く。

## 参考になる数値

- ある顧客では、マルチエージェントの構成が単一ループより約 2 倍遅かった。
- Anthropic は、より高度なモデル向けに Claude Code のシステムプロンプトを 80% 以上削った。スキルとツールの段階的開示による削減を含む。
- ツール定義が 30 から 50 を超えると、ツール選択が悪化しやすい。
- 評価セットは、模範例 10 件ほどから始められる。
- あるサポートエージェントの試験では、退行が 2 回の実行のうち 1 回にしか現れなかった。評価の各タスクは複数回実行する。

## 事例

- 顧客向けエージェントで、12 ほどの専門サブエージェントがあると、ブランドらしい体験を保ちにくく、遅延も増えた。
- よくある設計案は、意図分類器、固定の推論パイプライン、利用者層ごとの分岐、推薦の分岐、オーケストレーターの組み合わせである。助言は、明確なシステムプロンプト 1 つ、薄いデータツール 4 から 5 個、出力の確かなガードレールで多くの用途を賄えるというものだった。
- サポートエージェントで、あるサブエージェントを別のサブエージェントへ統合すると遅延は減ったが、手順が壊れた。メインのエージェントが、配送の専門家に確認すべき納期の質問へ、確認せずに答えた。

## 統合の手順

1. 小さな E2E の評価を先に作る。タスク完了を追い、統合後は正しいスキルを読み込んだか、正しいツールを呼んだかも確認する。
1. まずメインのエージェントがサブエージェントをツールとして呼ぶ構成で基準線を取る。
1. 利用が最も多い、または結びつきが強いものから、1 つずつ統合する。統合の前後を比べ、スコアが悪化したサブエージェントは残す。
1. サブエージェントのプロンプトはスキルに、API 呼び出しは MCP ツールに変える。ツールは API 単位でなく、利用者の意図ごとにまとめる。
1. 文脈とループを 1 つに共有し、ターン数やコストの上限はハーネスで設ける。
1. 参照資料は、プロンプトに貼らず、検索や参照のツールの後ろにある知識ベースに置く。
1. 最終スコアだけでなく、どのタスクの結果が変わったかを見る。本番のすべてのエージェント連鎖と、守るべきすべての規則を評価で覆う。

## 体制

- 小さな中央チームが、システムプロンプトと全体の品質を持つ。
- 各領域のチームが、自分のスキル、ツール、評価を持つ。

記事は、移行キットと、build-eval、prompt-audit、hillclimb、cost-optimize といった Claude API のスキルが使えるとも紹介している。
