# ワークフローの 3 つの基本パターンと選び方

複数ステップのエージェント処理に、どの実行パターンを与えるかを選ぶ判断材料をまとめる。
内容は Anthropic のブログ記事「Common workflow patterns for AI agents—and when to use them」（2026-03-05 公開）[^claude-blog] の要約である。
記事は「数十のチームとの仕事」を根拠に、本番の用途の大半は 3 つのパターンで足りると述べる。
記事に性能、コスト、レイテンシの測定値はない。著者名の表記もない。

## 基本の考え方

- 完全に自律するエージェントは、道具、順序、止め方を自分で決める。ワークフローは全体の経路、検査点、境界を先に決め、各ステップの中ではエージェントが推論し道具を使う。記事は工場の組み立てラインにたとえる。各工程は局所的に判断するが、全体の流れは設計済みである。
- 選び方を誤ると、レイテンシ、トークン、信頼性のどれかで損をする。
- 最も単純で動くパターンから始める。既定は sequential、parallel は遅延が支配的な独立作業にだけ足し、評価ループは品質の向上が測れるときにだけ足す。
- パターンは部品として独立している。ボトルネックの段に並列を足す、品質基準が上がったら評価を足す、といった後からの強化が、作り直しなしでできる。

## 3 つのパターン

### sequential

エージェントを固定の順序で並べ、各出力を次へ渡す。

- 向く場面: 依存のある作業、多段の工程、データパイプライン、下書き、レビュー、仕上げの流れ。各エージェントが 1 つの部分課題に集中でき、記事は精度が上がりうると述べる。
- 例: マーケティング文の作成のあとに翻訳する。抽出、スキーマ検証、データベースへの投入を順に行う。コンテンツのモデレーションで、抽出、分類、規則の適用、振り分けを順に行う。
- 避ける場面: 1 つのエージェントで全体を扱える。エージェント同士が受け渡しでなく協働する必要がある。手順を強いるだけで複雑さが増える。
- トレードオフ: 各段が前の段を待つので、レイテンシが増える。
- 実践: 先に、手順をプロンプトに書いた単一エージェントで試す。それが安定して失敗するときだけ分割する。

### parallel

独立した作業を複数のエージェントで同時に走らせ、結果を統合する。分散システムの fan-out と fan-in に近い。エージェント間の受け渡しはない。

- 向く場面: 独立した部分課題、1 つの課題への複数の視点、作業の区分け（片方が問い合わせを処理し、もう片方が安全性を審査するなど）、観点別の評価、投票。個々のエージェントを別のチームが持ち、別々に最適化できる利点もある。
- 例: 自動評価、脆弱性の種類ごとに分けたコードレビュー、文書分析（主題、感情、事実確認を並行して走らせて合わせる）。
- 避ける場面: 累積した文脈が要る。API の割当により並行が非効率になる。矛盾する結果への対処がない。統合が複雑すぎて品質を下げる。
- トレードオフ: 並行する API 呼び出しの分だけ費用が増え、統合の方式を決める手間が要る。代わりに、完了が早くなり、関心が分離する。
- 実践: 統合の方法を先に決める。多数決、確信度の平均、最も専門的なエージェントの判断を優先する、などがある。

### evaluator-optimizer

生成役が出力を作り、評価役が示された基準で評価し、生成役がその指摘で直す。品質の閾値か反復回数の上限で終わる。記事は、生成と評価は別の仕事であり、別のエージェントに分ける価値があると論じる。

- 向く場面: 測れる品質基準があり、AI の評価役が一貫して適用できる。初稿と最終版の質に実質的な差がある。
- 例: API 文書をコードベースと照らして完全性、明瞭さ、正確さで確認する。顧客宛てメールを口調と方針の遵守で確認する。SQL を効率と安全性で確認する。
- 避ける場面: 初回の品質で足りる。リアルタイムの応答が要る。基本的な分類のような単純な作業。基準が主観的。リンターのような決定的な道具で足りる。資源の制約が品質の利得を上回る。
- トレードオフ: トークンの使用量が倍々になり、反復の時間も増える。代わりに、構造化された指摘によって出力が良くなる。
- 実践: 開始前に最大反復回数と品質の閾値を決める。品質が頭打ちになったまま回り続ける高コストのループを防ぐ。

## トレードオフの一覧

| パターン            | 主な代償                   | 主な利点                       |
| :------------------ | :------------------------- | :----------------------------- |
| sequential          | レイテンシ                 | 集中した、より正確な部分課題   |
| parallel            | 費用と統合の手間           | 速さと関心の分離               |
| evaluator-optimizer | トークンと反復の時間       | 指摘による出力の改善           |

## 選択の指針

1. まず単一のエージェント呼び出しを試す。品質の基準を満たすなら、そこで終える。
1. 満たさないなら、何が足りないかを特定する。
   - 段階的な依存がある: sequential。
   - 独立した部分課題があり、速さが要る: parallel。
   - 反復で品質が測れるほど上がる: evaluator-optimizer。
1. どの選択でも、失敗時の扱いと再試行の方針を決める。レイテンシと費用の上限を見積もる。単一エージェントを基準線として置き、ワークフローが実際に効いているかを確かめる。

## 組み合わせ

パターンは入れ子にできる。evaluator-optimizer の評価役を複数にして並列に走らせる、sequential のパイプラインの一部の段を parallel にする、といった構成が記事に挙がっている。
