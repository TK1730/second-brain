# 長時間アプリ開発ハーネスの設計: generator と evaluator の分離

エージェントに数時間かかるアプリ開発を任せるとき、ハーネス（エージェントを包む足場）をどう組み、モデルが進むにつれてどう削るかの判断材料をまとめる。
内容は Anthropic の記事「Harness design for long-running application development」（2026-03-24 公開、著者 Prithvi Rajasekaran、Anthropic Labs）[^harness-article] の要約である。
記事の数値（所要時間、費用、反復回数）は著者自身の実験の報告であり、第三者による検証や統計的な比較ではない。

## 解こうとする問題

- 単純な長時間エージェントは、コンテキストが埋まるにつれて一貫性を失う。
- モデルによっては、コンテキストの上限が近いと思い込み、作業を早く切り上げる「コンテキスト不安」を示す。
- エージェントは自分の成果物を過大に褒める。デザインのような主観的な課題で特に目立つ。

## generator と evaluator の分離

GAN に着想を得て、作る役（generator）と採点する役（evaluator）を別のエージェントにする。

- 生成役に自分の成果へ厳しくなってもらうより、独立した評価役を厳しくなるよう調整するほうが、はるかに扱いやすい。
- 評価役も LLM なので、放っておくと甘くなる。調整は前提である（後述）。

## コンテキストリセットと引き継ぎ

| 方式         | 内容                                                         | 特徴                                                       |
| :----------- | :----------------------------------------------------------- | :--------------------------------------------------------- |
| リセット     | コンテキストを空にし、状態と次の手順を構造化して渡した新しいエージェントで再開する | まっさらな状態になる。オーケストレーション、トークン、遅延の負担が増える |
| コンパクション | 古い履歴をその場で要約する                                   | 連続性は保てるが、コンテキスト不安は消えない               |

- Claude Sonnet 4.5 ではコンテキスト不安が強く、リセットが不可欠だった。
- Opus 4.5 ではこの問題がほぼ消え、リセットをやめて、SDK の自動コンパクションによる 1 本の連続セッションで動かした。
- 記事の指針: リセットの要否はモデルで変わるため、使うモデルで確かめる。

## evaluator の調整

- そのままの Claude は QA 役として弱い。欠陥のある成果を自分で言いくるめて承認し、確認も表面的になる。
- 著者は、評価役の判断を自分の判断と見比べながら、プロンプトを数回にわたり調整した。
- 採点基準には、few-shot の例と詳細な点数の内訳を付け、好みに合わせてぶれを減らした。
- 評価役は、実行中のアプリを Playwright MCP で操作し、画面を撮り、基準ごとに採点して講評を書く。UI だけでなく API やデータベースの状態も確かめる。
- 評価役が見つけた例: 矩形の塗りつぶしツールが塗らない、削除の処理が条件を満たせず削除されない、ルートの定義順の誤りで 422 エラーになる。

## フロントエンドのハーネス

Claude Agent SDK の上に構築した。

- 4 つの採点基準: デザインの質、独創性、仕上げ、機能性。仕上げと機能性は既定でも十分だったため、デザインの質と独創性の重みを高くした。基準は、ありがちな「AI 臭い」パターンを減点した。
- 1 回の生成で 5 から 15 回反復した。全体で最長 4 時間かかった。
- 評価のたびに、生成役は今の方向を磨くか、美的に方向転換するかを選ぶ。
- 点数は上がってから頭打ちになり、余地は残った。「museum quality」のような語を入れると、デザインが特定の見た目へ寄った。
- 例: オランダの美術館のサイトで、9 回目は磨かれた暗い着地ページ、10 回目は CSS の遠近法とドア越しの移動を使う 3D のギャラリーへ大きく変わった。

## フルスタックのハーネス（3 役）

- planner: 1 から 4 文の指示を、製品の仕様へ広げる。範囲には野心的に、技術設計は高い抽象度にとどめる。早い段階の仕様の誤りが後へ波及しないようにするためである。フロントエンドのデザイン用スキルを渡して見た目の方針も決めさせる。
- generator: スプリント単位で 1 機能ずつ作る。構成は React、Vite、FastAPI、SQLite（のちに PostgreSQL）。スプリントの終わりに自己評価し、git を使う。
- evaluator: Playwright で動くアプリを操作する。スプリントごとに、製品の深さ、機能性、見た目、コードの質を採点し、各基準に厳格な閾値を置く。1 つでも下回ればスプリントは失敗となる。
- スプリント契約: 実装の前に、生成役が「完了」の定義と確認方法を提案し、評価役が合意するまで見直す。エージェント間はファイルで連絡する。

## 数値と結果（著者の自己報告）

### レトロゲーム作成ツール（Opus 4.5）

2D のレトロゲーム作成ツール（レベル編集、スプライト編集、エンティティの挙動、試遊モード）を作らせた。

| 構成               | 所要時間 | 費用  | 結果                                                         |
| :----------------- | :------- | :---- | :----------------------------------------------------------- |
| 単独のエージェント | 20 分    | $9    | 部品は並ぶが、入力に何も反応しない。定義が実行系へ配線されていなかった |
| フルのハーネス     | 6 時間   | $200  | 16 機能、10 スプリントの仕様。より洗練され AI 連携も備わるが、操作に迷う箇所と粗い物理が残った |

- 費用は 20 倍を超える。スプリント 3 だけで契約の基準が 27 個あった。

### DAW（更新後のハーネス）

「Web Audio API でブラウザ上に多機能な DAW を作る」を指示した。記事は、この実行のモデル名を明記していない。

| 段階           | 所要時間   | 費用      |
| :------------- | :--------- | :-------- |
| planner        | 4.7 分     | $0.46     |
| 構築（1 回目） | 2 時間 7 分 | $71.08    |
| QA（1 回目）   | 8.8 分     | $3.24     |
| 構築（2 回目） | 1 時間 2 分 | $36.89    |
| QA（2 回目）   | 6.8 分     | $3.09     |
| 構築（3 回目） | 10.9 分    | $5.88     |
| QA（3 回目）   | 9.6 分     | $4.06     |
| 合計           | 3 時間 50 分 | $124.70 |

- 構築役は、スプリントなしで 2 時間以上一貫して動いた。それでも QA は、クリップをドラッグできない、楽器パネルやエフェクトの可視化がない、録音が仮実装、クリップの伸縮と分割がない、といった実際の穴を見つけた。
- 結果は、動作するアレンジ画面、ミキサー、トランスポートで、指示だけで短い曲を最後まで作れた。ただし著者は、プロ水準にはほど遠いこと、作曲能力が弱いこと、Claude が音を聞けないため音楽面の QA に限界があることを認めている。

## 簡素化の指針（Opus 4.6 での見直し）

著者の原則は「可能な限り単純な解から始め、必要になったときだけ複雑にする」である。

- スプリントの仕組みを外した。モデルが自力で作業を分解できるためである。
- planner は残した。なくすと生成役が範囲を小さく見積もった。
- evaluator は、スプリントごとの採点をやめ、最後に 1 回だけ回す形にした。
- 見直しの方法は、部品を 1 つずつ外して影響を測ることである。一度に全部外す試みは、先に失敗している。
- 評価役の費用が見合うのは、課題がモデルの単独での確実な範囲を超える部分だけである。この境界は、4.6 で外側へ動いた。

## 教訓

1. 使うモデルで実験し、現実的な課題の実行記録（トレース）を読み、それに合わせて調整する。
1. 課題の分解と専門化したエージェントは、複雑な作業で余地を広げうる。
1. モデルを更新するたびにハーネスを見直す。もう効いていない部品を外し、新しい能力を引き出す部品を足す。
1. 記事の見方では、モデルが良くなってもハーネスの設計空間は縮むのではなく移動する。
