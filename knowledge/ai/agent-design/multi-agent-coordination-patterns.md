# マルチエージェントの 5 つの協調パターンと選び方

マルチエージェントを作ると決めたあと、エージェント同士の協調をどの型で組むかを選ぶ判断材料をまとめる。
内容は Anthropic の記事「Multi-agent coordination patterns: Five approaches and when to use them」（2026-04-10 公開、著者 Cara Phillips）[^claude-article] の要約である。
記事には性能の測定値、コスト、成功率はない。数値に見えるのは、完了検知の説明に使う例示の所要時間（2 分と 20 分）だけである。

## 基本の考え方

- 最も単純で動きそうな型から始め、詰まる箇所を観察して発展させる。洗練されて聞こえるという理由で型を選ばない。
- 型は排他的な選択ではなく部品である。実運用では組み合わせることが多い。
- 選択は、文脈の境界と情報の流れで考える。分割は作業の種類ではなく、各エージェントが必要とする文脈で決める。
- 検証の基準と終了条件を明示する。記事は、この 2 つを最も多い失敗点として繰り返し挙げている。

## 5 つのパターン

### generator-verifier

生成役が出力を作り、検証役が基準に照らして評価する。却下は理由つきで生成役へ戻り、受理されるか反復の上限に達するまで繰り返す。

- 向く場面: 出力品質が重要で、評価基準を明示できる。テスト付きのコード生成、事実確認、ルーブリック採点、コンプライアンス確認など。
- 例: サポートの返信メールを下書きし、検証役が知識ベースとの正確さ、ブランド指針に沿った口調、各問い合わせへの対応漏れを確認する。
- 弱点:
  - 検証は基準の質に尽きる。「良いか」のような曖昧な確認は何でも通し、品質管理をしているという錯覚を生む。
  - 生成と検証が分けられることが前提になる。判定が生成と同じくらい難しいと、問題を見逃す。
  - 反復が振動することがある。上限を設け、人への引き上げや注記つきの最善案の返却を退避先にする。

### orchestrator-subagent

主導役が計画、委任、統合を担い、サブエージェントが特定の責務を処理して結果を返す。各サブエージェントは自分の文脈を持ち、要点だけを返す。Claude Code は、主エージェントが多くの作業を自分で行い、大規模なコードベース検索のような作業だけをサブエージェントへ出す例として挙げられている。

- 向く場面: 課題の分解が明確で、部分課題同士の依存が小さい。
- 例: 自動コードレビューで、セキュリティ、テストの網羅、スタイル、アーキテクチャの確認を別々に出し、1 つのレビューへ統合する。
- 弱点:
  - 主導役が情報の詰まりどころになる。サブエージェント間の知見は主導役を経由するため、何度も受け渡すうちに詳細が失われたり要約で消えたりする。
  - 明示的に並列化しないと逐次で走る。その場合は、速度の利点なしに、マルチエージェント分のトークン費用だけを払う。

### agent teams

調整役が持続するワーカーを起動し、ワーカーは共有キューから課題を取り、複数ステップを自律的にこなして完了を知らせる。orchestrator-subagent との違いは持続性である。サブエージェントは 1 つの限られた課題で終わるが、チームメイトは生き続け、文脈を蓄え、専門化する。調整役は課題ごとにワーカーをリセットしない。

- 向く場面: 部分課題が互いに独立で、長く続く複数ステップの作業が効く。
- 例: 大規模なコード移行で、サービスごとに 1 人のチームメイトが依存更新、コード変更、テスト修正、検証を担う。最後に調整役が統合テストを走らせる。
- 弱点:
  - 独立性が前提になる。中間の知見を共有しにくく、出力が衝突することがある。
  - 所要時間がばらつくため、完了の検知が難しい。
  - 同じコードベース、データベース、ファイルを触ると編集が衝突する。分担を丁寧に切り、衝突の解決を用意する。

### message bus

エージェントは publish と subscribe で通信する。トピックを購読し、ルーターが一致するメッセージを届ける。既存の配線を変えずに、新しいエージェントを加えられる。

- 向く場面: ワークフローが固定の順序でなく、イベントから生まれる。エージェントの顔ぶれが増える見込みがある。チームごとに独立して開発、配備したい。
- 例: セキュリティ運用で、トリアージ役がアラートを分類してネットワーク調査役か ID 調査役へ送る。調査役は文脈収集役へ補足を依頼でき、結果は対応の調整役へ流れる。
- 弱点:
  - 追跡が難しい。複数のエージェントにまたがる連鎖を追うには、丁寧なログと相関付けが要る。
  - ルーティングの精度が重要になる。誤配や取りこぼしは黙って失敗し、システムは落ちないまま何も処理しない。LLM のルーターには固有の失敗もある。

### shared state

エージェントは、データベース、ファイルシステム、文書などの永続ストアを読み書きし、中央の調整役を置かない。初期化がストアに種をまいて始まり、時間切れ、収束の閾値、指名したエージェントによる十分との判断などの終了条件で終わる。

- 向く場面: エージェントが互いの発見の上に積み上げる共同作業。単一障害点をなくしたい場合。
- 例: 学術文献、業界レポート、特許、ニュースを担当するエージェントによる調査の統合。ストアに入った発見はすぐ他のエージェントに見える。
- 弱点:
  - 作業の重複や矛盾した方針が起きうる。挙動が相互作用から生まれるため、結果の予測もしにくい。
  - 反応ループが難所である。互いの書き込みに反応し続け、収束せずにトークンを使い続けることがある。時間の予算、「N 回の周期で新しい発見がない」という規則、判定役の指名など、終了条件を最初から設計する。後付けにすると、延々と回るか、唐突に止まる。
  - 作業の重複や同時書き込みには、ロック、版管理、分割といった既知の対策がある。

## 選択の指針

| 状況                                         | パターン                |
| :------------------------------------------- | :---------------------- |
| 品質が重要な出力で、評価基準が明示できる     | generator-verifier      |
| 課題の分解が明確で、部分課題が限られている   | orchestrator-subagent   |
| 並列の作業量があり、独立した長い部分課題     | agent teams             |
| イベント駆動の流れで、エージェントが増える   | message bus             |
| 共同の調査で、発見を共有する                 | shared state            |
| 単一障害点を許せない                         | shared state            |

迷ったときの比較は次のとおりである。

- orchestrator-subagent と agent teams: 短く限られた部分課題なら前者。ワーカーが複数の周期にわたり文脈を保つ必要があるなら後者。
- orchestrator-subagent と message bus: 手順があらかじめ分かっているなら前者。発見したイベントでワークフローが変わるなら後者。主導役に条件分岐が積み上がってきたら、message bus に切り替えるとルーティングが明示され、拡張しやすくなる。
- agent teams と shared state: 分担が互いに干渉せず、最後に結果を合わせるなら前者。リアルタイムに互いの知見が要るなら後者。
- message bus と shared state: 個別のイベントが段階的な処理を起動するなら前者。時間とともに積み上がる知識なら後者。message bus には中央のルーターが残るので、単一障害点の除去を優先するなら shared state が合う。

## 進め方

1. まず orchestrator-subagent から始める。記事は、最小の協調コストで最も広い課題を扱えると述べる。
1. 持続性、イベントのルーティング、リアルタイムの協働といった具体的な必要が出てから、他の型へ移る。
1. 組み合わせを恐れない。全体の流れは orchestrator-subagent、協働が要る部分課題だけ shared state、といった構成や、message bus がイベントを agent teams 型のワーカーへ配る構成が例に挙がっている。
1. generator-verifier を入れるなら検証基準を、shared state を入れるなら終了条件を、先に書き出す。
