# Claude Code で評価の設計と改善の反復を自動化する

Claude Code の `claude-api` スキルが持つ 2 つのコマンドで、評価（eval）を作り、その評価を使ってアプリを 1 変更ずつ改善する手順をまとめる。
内容は Lance Martin による記事（2026-09-28 公開）[^claude-article] の要約である。
記事の数値は Anthropic 内部のベンチマークと、API ドキュメント由来のテストセットで得た結果であり、別の業務にそのまま当てはまるとは限らない。

## 準備

- `claude update` で更新し、Claude Code から `/claude-api build-eval` と `/claude-api hillclimb` を呼ぶ。
- 記事はこれらをベータや研究プレビューとは記していない。

## 良い評価の 4 条件

1. タスクが本番を反映している。作りやすさや採点しやすさで選ばない。
1. モデルの能力や effort（推論の労力設定）に応じて点が伸びる。伸びないなら、曖昧なタスクか採点器のずれを疑う。
1. 最上位でも満点にならない余地がある。毎回失敗するタスクは警告である。良いタスクは、2 人の専門家が同じ判定をし、採点対象が全てタスク文に書かれている。
1. 実行ごとのばらつきが小さい。原因は、曖昧なタスク、同じ出力への採点のぶれ、effort 設定の不統一、答えが漏れる環境の残留状態（ファイルや git 履歴）である。

今のモデルが失敗する例だけを選ぶと、特定モデルの癖を測ることになる。人が「難しい」と説明できる例を選ぶ。本番の障害、バグ報告、チケットが良い入手元で、利用者のログだけだと易しい側に偏りやすい。

## build-eval の流れ

1. 入力を集める。優先順は、本番のトランスクリプト（保持期間と機微情報を確認したうえで）、バグ報告とサポートチケット、手書きの 5 から 10 件、コードベースから合成した例（実例を少し混ぜる）である。一覧のレビューページで確認する。記事の例は、受信箱の振り分けで 24 件を分類と難易度で付箋づけしている。
1. 採点器を選ぶ。出力が限定的なら、完全一致、固定ラベル、スキーマ検証、テスト合格などのプログラム検証を使う。自由記述なら LLM 判定を使い、1 から 5 の点ではなく、確認できる主張の基準表で採点させる。基準との比較では、順序を乱し、どちらが基準か伏せる。判定モデルは評価対象と別にする。
1. 基準線を走らせる。件数、繰り返し、モデルから規模と所要時間を見積もり、平均点と信頼区間を出す。

成果物は、ケース、採点器、実行スクリプト、ケースごとの JSON 行と全文トランスクリプト、各ケースへリンクする結果ページである。結果ページは既定でネットワークを使わない静的ファイルである。
採点した例を読み、自分なら違う点をつけたかを確かめてから採点器を信用する。

基準線の実行中に、次の点検が行われる。

- 採点器の一貫性: 同じ出力を 2 回採点し、判定が変わると報告する。
- 配管: タイムアウト、API エラー、途中で切れた回答を調べ、インフラの雑音をばらつきと取り違えない。
- 余地: 基準点が約 95% 以上なら、品質ではなくコストや遅延の改善を狙うよう警告する。

## hillclimb の流れ

改善する対象は次の観点で選ぶ。

- 反復が安い: プロンプトやスキルの文面は直しやすい。ハーネスのコードを広く変えるのは高くつく。
- 原因をたどれる: 点の変化が編集箇所に結びつく（例: スキルの説明文とトリガー率）。
- 範囲が絞れている: 「性能を上げる」だけでは止まる。飽和した評価でも、同等の点で安い構成を探せる。

対象は、システムプロンプト、スキルや指示ファイル、ツールの説明、モデル、effort、API パラメータ、ハーネスのコードから選ぶ。

各ラウンドの手順は次のとおり。

1. 評価セットを学習用と保留のテスト用にランダムに分ける。
1. 開始前に、評価の雑音が、実行に移す最小の改善より小さいかを確かめる。大きければ繰り返しや件数を増やす。
1. 前ラウンドの学習用トランスクリプトを読み、根本原因に効くパッチを 1 つ提案する（1 行の言い換えではなく、原因の節の書き直しや欠けた規則の追加）。
1. 評価し、学習とテストの両方が上がれば採用する。学習だけ上がってテストが横ばい（過学習の疑い）か、どちらかが下がれば戻す。
1. 2 から 3 ラウンド点が止まったら、残る学習側の失敗を原因別に仕分ける。曖昧なケース、ハーネスの不具合、ばらつきが見つかることがある。

過学習を防ぐ要点は次のとおり。

- 失敗した内容をプロンプトへ貼らない。評価でしか要らない道具や規則を足さない。
- 答えをモデルの手が届かない構造にしておく。モデルが公開リポジトリから参照解答を取るなど、答えを直接探す報酬ハックが起こりうる。
- 終了時は、テストで最良だったバージョンで止め、基準線との差を信頼区間つきで報告する。差が雑音の範囲なら、マージしないよう勧める。

## 数値例

サポート業務の内部ベンチマーク（44 件、探索 30 件と保留 14 件）では、段階的な見直しで次の結果を得た。

| 段階                                         | 精度    | 1 件あたりの費用 |
| :------------------------------------------- | :------ | :--------------- |
| 開始時（Opus 4.8、既定の high effort）       | 74.4%   | 4.6 セント       |
| プロンプトの整理後、Opus 5.5 の low effort   | 87.8%   | 1.9 セント       |
| Sonnet 5 の low effort                       | 88.9%   | 約 1 セント      |
| 振り分け規則などを足した Sonnet 5            | 98.9%   | ほぼ同じ         |

保留側では元の構成 78.6% に対し最終構成 90.5% で、費用は約 5 分の 1 だった。
記事は、費用減の一部を Opus 5.5 の価格（入出力トークンが Opus 4.8 より 20% 安く、キャッシュ読み取りが 60% 安い）にも帰している。

claude-api スキル自体の改善では、基準 66.1% から約 88% へ上げた。
欠けた機能の追記、古い API 形の対応表（訓練時の記憶に引かれて古い書き方になる問題への対処）の追加、誤った 2 つの採点器の修正が効いた。
採点器の誤りは、不要な手順を要求するものと、ドキュメントと食い違うものだった。

## 注意点

- 評価の質が最大の制約である。飽和した、曖昧な、雑音の多い評価では、改善が止まるか、誤った向上が出る。
- 学習とテストを分けても過学習はありうる。マージ前に保留側の結果を確かめる。
- 不正な課題や採点器による失敗は、後続のラウンドに使わず、除くか直す。
