# LLM による形式検証を大規模に使う手順と注意点

LLM に形式証明を書かせ、オープンソースライブラリの安全性を大規模に検証した取り組みの要点をまとめる。
内容は Anthropic の Frontier Red Team と Theorem の記事（2026-10-22 公開）[^anthropic-research] の要約である。
数値はすべて著者らの自己申告で、独立した再現は報告されていない。証明の一部は公開されており、確認を呼びかけている。

## 何をしたか

- コンパイル済みの実行ファイル（RISC-V アセンブリ）に対し、「クラッシュしない」という性質を証明した。
- 既存のファズテストを、その性質を述べた形式仕様に変換した。
- Claude が、仕様が成り立つことの Rocq の証明を書き、Rocq の検証器が確かめた。
- 証明中にバグが見つかったら、コードを直し、仕様を作り直し、新しい仕様を証明した。

## 手順

1. ライブラリと既存のファズテストを RISC-V にコンパイルする。
1. バイナリに、Theorem が作った RISC-V と Linux プロセスの意味論、およびクラッシュしない性質を組み合わせて仕様を作る。
1. Claude が仕様を証明する。到達できるクラッシュがあれば修正する。
1. Rocq のカーネルで証明を検査する。レビューで信頼すべき対象は、モデル、定理の記述、検査器に絞れる。

## 規模と成果

- 123 のライブラリ、239 の入口（OSS-Fuzz）を対象にした。
- 64 MB 未満のどの入力でもクラッシュしないことを、前提つきで示した。
- 証明は合計で約 1.8 億行の Rocq で、典型的な 1 件は約 60 万行である。バイナリ長の中央値は約 1.8 万命令。
- 期間は「数週間」。証明には数億トークンが必要なものがある。
- 「数百」のバグを見つけた。数兆回のファズテストで見逃されていたものを含む。例として、カウンタのアンダーフローによる範囲外書き込み（約 20 MB の入力が必要）、64 MB の入力と 2 GB 超のメモリが必要な範囲外読み取り、libexpat の既知の脆弱性の再発見がある。
- zlib は RFC 1950 から仕様を書かせ、Linux カーネルの zlib を x86 バイナリの水準で証明した。ほかの約 6 つのライブラリでも繰り返し、悪用できない軽微な不具合だけが見つかった。
- Rust 製の Python インタプリタは、Verus で CPython の意味論に対して検証した。170 万本のランダムなプログラムで 99.95% が CPython と一致した。
- PDF リーダーでは、通常 1 年かけて報告される数のセキュリティバグを 1 週間で見つけた。

## トークンの効率

- 小さな 36 課題で、Opus 5.5 は Opus 5 より約 40% 少ないトークンで半数を証明した。
- 証明の作業場を共有した複数のエージェントは、単独のエージェントより 17% 少ないトークンで済んだ。
- 共通のランタイムの証明は複製して調整でき、共有部分に新しいコードはほぼ要らなかった。

## 注意点

- 「形式検証済み」は「バグなし」ではない。信頼する部品（Rocq、RISC-V と Linux の意味論）や、仕様と実機の差に不具合が残りうる。
- 証明の対象は、musl libc に静的リンクした単一スレッドの RISC-V バイナリである。実運用の多くは x86 や ARM で、動的リンクの glibc を使う。
- すべての入口を検証したわけではない。到達できないコード、呼び出し側の誤用は範囲外である。AddressSanitizer はすべてのメモリバグを検出しない。
- 報酬ハッキングの恐れがある。コードを書き換えて「絶対に落ちない」ようにすれば、証明は通るためだ。対策として、修正にはペナルティを与え、修正が変える入力の少なさを証明すれば報酬を与え、ログを監査した。
- トークンの費用は依然として大きい。著者らは下がると見込んでいる。

## 実務への示唆

- 以前のモデルで試して諦めた人も、再挑戦する価値があると記事は勧めている。
- 既存のファズテストがあれば、形式検証の入口にできる。
- Anthropic は証明の一部、信頼する部品、未証明のファズ仕様を公開した。Theorem は他のオープンソースへの適用を申し出ており、始めるための Claude のスキルも公開している。
- 今後の課題は、x86 と ARM のモデル化、動的リンク、呼び出し側の契約である。
