# Claude Tag をスタートアップで使い始める

Slack のチャンネルで Claude にメンションし、コネクタをつなぎ、チームでタスクを割り当てたり進捗を操縦したりする「Claude Tag」の使い始め方をまとめる。
内容は Anthropic の記事「The Claude Tag guide for startups」（2026-11-13 公開）[^claude-article] の要約である。
事例と数値は、取材先の企業が提供した自己申告であり、独立した検証はされていない。
Claude Tag はパブリックベータである。

## 導入先チャンネルの 5 つの型

取材した 8 社は、次の型のいずれかから始めていた。

| 型                     | 例のチャンネル                                       | Claude の動き                                                                                   |
| :--------------------- | :--------------------------------------------------- | :---------------------------------------------------------------------------------------------- |
| オンコール             | #on-call, #alerts-ci, #deploy-watch                  | アラートごとにスレッドを立て、既存チケットを確認し、データを見てから原因を示し、担当者にタグ付けする。修正が限定的なら下書き PR を作り、不要なら「対応不要」と言う |
| スレッドから下書き PR  | #quick-wins, #bug-bash, #feature-requests            | 1 リクエスト 1 スレッドで、チケットとコードを読む。不足なら質問し、小さな変更なら下書き PR を作る。マージはしない。大きすぎるか危険なら理由を述べてチケット化を提案する |
| 社内ナレッジ           | #ask-anything, #company-wiki                         | 出典リンク付きで答える。資料が食い違えばコードで確かめ、古い資料を指摘する。自信がなければ担当者にタグ付けする |
| セルフサービスデータ   | #data-requests, #metric-definitions                  | 管理されたモデルと定義だけで答える。データがなければ「未検証」と答え、結論、数値、要因、注意点の順に書く。同じ質問が続けば定期実行を提案する |
| 定例レポートと引き継ぎ | #sales-pipeline, #customer-handoffs, #qbr-prep       | 定期実行で下書きを専用スレッドに投稿する。変更点と判断が必要な点を先頭に書き、確認済みと仮定を分ける。人が承認するまで外部には出さない |

主な連携先は、GitHub、GitLab、Linear、Jira、Sentry、Datadog、PagerDuty、Notion、Google Drive、Metabase、dbt、BigQuery、Snowflake、Salesforce などである。

## 事例の数値

| 企業          | 結果                                                                         |
| :------------ | :--------------------------------------------------------------------------- |
| Campfire      | Slack でのメンションから下書き PR まで 21 分                                 |
| NavigateAI    | アラートから根本原因の特定まで 8 分、マージまで 93 分。約 90 チャンネルで運用 |
| Moritz        | 社内の質問応答が最大 30 分から 2 分未満、終業時の日報が約 1 時間から 5 分     |
| Orderful      | Slack の依頼から本番まで約 2 日。Claude Tag の接続は 30 分未満                |
| Descript      | 定例レポートの準備が数日から数時間                                           |

## 導入手順

1. **前提を確かめる**: Claude 組織の Owner と Slack ワークスペースの管理者が要る。管理者が Routines を有効にする。Team プランでは、応答の前に利用クレジットが要る。
1. **バンドルでアクセスを渡す**: Claude はサービスアカウントの独自のエージェント ID で動く。コネクタ、リポジトリ、指示をバンドルにまとめ、組織、ワークスペース、チャンネルのいずれかの単位で付与する。最初の 1 チャンネルに必要な分だけに絞る。
1. **非公開チャンネルで試す**: 取材先のほぼ半数が、少人数の混成チームの非公開チャンネルから始めた。
1. **利用範囲を決める**: 既定では、Claude アカウントのない Slack メンバーも使える。組織で制限するか、Claude のいるチャンネルに検索を限れる。Enterprise ではロールやチャンネル単位でも制限できる。
1. **できること・できないことを書く**: 下書き PR は作ってよいが、マージは人が行う。インフラ変更、監査、機密データは別のツールに任せる。
1. **セキュリティレビューを早く始める**: データ保持とアクセス範囲を確かめる。
1. **予算とアラートを決める**: 使用量課金である。全体とチャンネル別に上限を置け、モデルはチャンネル単位で選べる。Orderful は組織全体の上限を置き、75% と 90% で通知している。最初のチャンネルの実コストを、次の見積もりに使う。
1. **1 つの業務から始める**: すでに使っているチャンネルで 1 業務に絞り、信頼されている人にオープンな場で先に使ってもらう。
1. **反応の頻度を調整する**: 反応しすぎも、毎回メンションが要るのも問題になる。
1. **個人コネクタに注意する**: 依頼した本人の権限で動く。機密性の高いものは「レビュー付きで許可」にする。回答は必ずチャンネルに投稿される。

## 運用のコツ

- 指示は新入社員への説明のように書く。最初に確認すること、PR を開く条件、質問する条件、「対応不要」も正しい答えであることを入れる。
- オンコールの手順と、インシデントごとの学びをファイルに残し、Claude に読ませる。
- スレッドにサンプルファイル、顧客のメッセージ、スクリーンショットを入れると、推測でなく実物に基づいて作れる。
- データの質問は、先にデータチームが主要モデルと指標定義を文書化する。回答の質は、Claude が持つ文脈で決まる。
- 修正は DM でなくチャンネルのスレッドで伝える。恒久的に直すなら、チャンネルのメモリの更新を頼む。
- 二度頼んだ作業は定期実行にする。
- 「このチャンネルで何を学んだか、どの用途に広げられるか」と Claude に聞くと、次の活用先を提案する。

## 提供条件

- Team と Enterprise プランで使える。Free、Pro、Max では使えない。
- ZDR、CMEK、HIPAA 構成の組織では使えない。BAA の対象外でもあるため、導入前に確かめる。
- 具体的な金額は記事にない。
