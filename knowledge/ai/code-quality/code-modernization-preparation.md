# AI 主導のコード近代化プロジェクトを 6 段階で準備する

銀行基盤のような重要・規制対象のシステムを、AI エージェントで近代化するときの準備手順をまとめる。
内容は Anthropic の記事「How to prepare for an AI-led code modernization project」（2026-09-23 公開）[^claude-article] の要約であり、著者の現場経験に基づく推奨である。形式的な方法論ではない。
記事は、数年かかった作業が数か月から数週間に縮む一方、変更管理・レビュー・承認は変わらないと述べる。ボトルネックは「変更を作ること」から「承認する組織を動かすこと」に移る。

## 全体の流れ

1. 目標を定める
1. 証明条件（certificate）を定める
1. 昇格ポリシーを決める
1. 前提条件を整える
1. エージェントのワークフローを作り、磨く
1. 実行する

## 1. 目標を定める

近代化の種類を最初に 1 つ選ぶ。

| 種類        | 内容                                           | 選ぶ場面                                   |
| :---------- | :--------------------------------------------- | :----------------------------------------- |
| Uplift      | 同じ技術スタックでバージョンを上げる（例: C++11 から C++20） | 技術は健全だが、サポート切れや脆弱性で版が古い |
| Transform   | 振る舞いを保ったまま別スタックへ移す（例: COBOL から Java） | スタックが問題で、現在の振る舞いは信頼できる |
| Reimagine   | 新しい構成で作り直し、振る舞いも変える         | コードと一緒に振る舞いも変える必要がある   |

- 種類は立場で意見が割れやすい。本番に近い人は Transform、古参は技術的負債の返済、事業側は新要件を望む。放置すると、後で「変更が正しいか」の議論として再燃するため、早く決める。
- コードベースを地図化し、挙動を文書化する。Claude は依存関係の把握や、忘れられた業務フローの文書化ができる。記事が紹介するコード近代化プラグインの assess、map、extract-rules は、ビジネスルールを出典付きで取り出す。
- Claude の抽出は不完全なことがある。業務利用者や開発者への聞き取りと社内文書で補う。Reimagine は、利用者グループと合意した振る舞いの仕様書が追加で必要になる。
- 近代化の理由は、コスト削減よりリスク低減が最も強い。未修正の脆弱性、事業を止めかねない障害、サポート切れの実行環境、システムを知る技術者の減少が該当する。
- 難所は多くの場合、社内の合意形成である。経営層向けの事業ケースを用意し、「変えるリスク」と「変えないリスク」の比べ方に合意しておく。

## 2. 証明条件（certificate）を定める

certificate は、すべての変更が満たすべき条件とテストの集合である。人手を介さずに検証できる条件だけで構成し、エージェントが通るまで反復するか、人のレビューへ回せるようにする。
記事は 11 の例を挙げる。

- 元のテストスイートが通る。Claude が書いたテストも通る。
- カバレッジが合意した水準に達する。性能ベンチマークが合意した範囲に収まる。
- 新しい文脈で行う Claude の独立した敵対的レビューで、ブロッキングな指摘が出ない。
- computer use による UI 確認で退行がない。
- 同じ入力に対して旧版と新版が同じ出力を返す（実入力、記録した入力、Claude が作った入力）。
- 永続データとワイヤ形式が新旧間で往復できる。
- 段階的な本番展開の期間中、エラー率・遅延・アラートが悪化しない。
- 静的解析とセキュリティスキャンで新規の指摘がない。コンパイル型ではビルドが警告なく通る。

実践上の要点は次のとおり。

- 現行コードに依存する開発者、利用者グループ、事業責任者を早い段階で巻き込む。条件づくりに知見が入り、レビュー時の支持も得やすい。証明条件が強く明確なら、次の昇格ポリシーを軽くできる。
- Uplift は元のテストと旧コードとの同等性が核になる。Transform は旧テストが新スタックで動きにくいため、本番トラフィックの再生、差分テスト、並行運用が中心になる。
- Reimagine は最も難しい。仕様は既存コードより客観性が低く、モデルの判断が増え、結果がぶれうる。仕様から書いたテスト、独立レビュー、差分確認に頼り、仕様の穴はここで最初に露見するため改訂を見込む。
- 旧システムはテストやテレメトリが乏しいことが多い。その欠落を洗い出すのも作業の一部で、並行運用環境、再生ハーネス、追加テストを Claude に作らせて証拠を補える。

## 3. 昇格ポリシーを決める

昇格ポリシーは、変更ごとに人がどこまで深く見るかを定めた、合意済みの段階的レビュー経路である。エージェントは人が読める速度を超えて変更を出すため、これがないと終わらない。

- 変更を影響範囲とエージェントへの信頼度で段階分けする。既存のリスク分類があれば流用し、重要経路は人の全面レビューを残す。
- 繰り返し付くフラグは、1 件ずつ見ずに、ワークフローか証明条件の側で根本から直す。
- レビュアーが最も速く判断できる情報と出力形式を、先に合意する。早期のサンプル出力で確認してもらう。
- 領域の専門家（SME）は最終差分を全件読まない。最もリスクの高い段階と、エージェントが判断に迷って上げた事項に時間を使ってもらう。
- 専門家に早期から関わってもらうと、本番前に証明条件を調整でき、承認済みサンプルを根拠に、確度の高い変更を軽い経路に回せる。従来の「最後にレビュー」を逆転させる発想である。
- 期限が厳しい（サポート切れが迫る）場合は、変更ごとのリスク増を明示的に受け入れて軽いレビューにする。余裕があれば深いレビューを選ぶ。
- 規制環境では、承認者個人が不具合のリスクを負うため軽いレビューをためらう。経営層が方針を事前に示し、本番に出た不具合の責任を分担する。

この方式は、詳細な証明条件と、Claude がどう変更に至ったかを理解したレビュアーがいて初めて成立する。

## 4. 前提条件を整える

多くは基盤、QA・リリース、セキュリティ・コンプライアンスなど、プロジェクト外のチームが握る。各チームには別の滞留案件と承認手続きがあるため、手順 1 から 3 と並行して早く依頼する。

- 環境: ワークフローを動かす専用のリモートホスト、証明条件を支えるテスト容量、本番テレメトリや本番に近いデータ。
- コードと CI/CD: ビルドログ・インポート解析・実行時トレースから作る依存関係の地図、依存パッケージの方針、CI/CD の互換性チェック、コードフリーズの方針、開発者への周知計画。
- チームとレビュー: 依存する他チームの関与方法（証明条件の承認、昇格ポリシーのレビュー）の合意と、レビュー時間の確保。
- セキュリティ: ソースを Claude Code に送る承認済みの経路。最小権限（近代化用ブランチにのみ書き込み、本番の認証情報なし）。秘密情報と個人情報を除去またはマスクしたブランチ。全変更の追跡（各 PR にエージェントの履歴と証明条件の証拠を紐づける）。新規依存のライセンスと脆弱性の確認。

## 5. エージェントのワークフローを作り、磨く

公開されているコード近代化プラグインを出発点に、Claude Code でカスタムのワークフローを作る。

1. 知識ベースを用意する。目標、証明条件、昇格ポリシー、コード、文書、必要なデータやツールを、Claude が読めるファイルシステムか MCP サーバーに置く。
1. ワークフローを組む。コード固有のスキルや抽出したルールなど、Claude の出力は下流で使う前に人が確認する。
1. コードベースの一部でパイロットを回し、変更、エージェントの過程、証拠をレビューする。
1. 問題は個別の変更を直さず、ワークフロー側を直す。変更が安定して証明条件を満たし、レビュアーが自信を持てる状態を目指す。

## 6. 実行する

- 小さい範囲で、レビューと昇格まで含めて端から端まで終わらせる。安いうちに問題を直し、確信が持てたら全体へ広げる。
- Transform と Reimagine は、既存システムの隣に新システムを作り、準備ができたら切り替える。
- Uplift は、開発を続けながら稼働中のコードを近代化する方法もある。止められないシステムや、別コピーを保てないほど変化が速い場合に向く。コードを論理的な区画に分け、1 区画ずつフリーズして更新し、CI/CD で完了済みの区画が新しいコミットで戻らないようにする。

## コスト見積もり

記事は具体的なトークン数や金額を示していない。見積もり方の考え方のみを述べる。

- コスト要因は、読み書きするコード量、証明条件の検証作業（規制環境では大きな割合になる）、テストの作成と修正、周辺チームの調整負荷である。
- 小さなパイロットでトークン使用量を測り、残りの範囲へ外挿する。調整負荷のようにパイロットで測れないものは未知として残す。得られる値は下限であり、確定見積もりではない。
- 最適化の案として、最もトークンを使う箇所を見つけて安い手段を探す。重い検証は安いゲートを通ってから実行する。証明条件が全面的に検証できる大量の機械的作業には Sonnet のような低コストのモデルを使い、難しい変換と敵対的レビューには高性能なモデルを残す。安いモデルが証明条件を満たせないときだけ高いモデルへ上げ、再試行率はパイロットで分析する。

## 成果物の再利用

近代化後のコードだけでなく、ワークフロー、書かれた証明条件、受け入れられた昇格ポリシー、変更ごとの証拠の記録が残る。これらを、次回のアップグレードや書き換え用の手引きとして整理できる。
