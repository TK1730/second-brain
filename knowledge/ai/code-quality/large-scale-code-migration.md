# Claude Code で大規模コード移行を進める 6 段階

Anthropic が Claude Code で大規模なコード移行（言語やスタックの載せ替え）をどう進めているかをまとめる。
内容は Anthropic の記事「How Anthropic runs large-scale code migrations with Claude Code」（2026-07-16 公開）[^claude-article] の要約である。
記事の数値はすべて記事側の自己申告で、第三者による検証は示されていない。
記事自身も、手順は一般化した出発点であり、紹介する 2 つの移行（Zig から Rust、Python から TypeScript）がそのまま使った手順ではないと断っている。

## 事例の概要

- Bun（Zig から Rust）: 約 100 万行を 2 週間未満で生成した。マージ前に既存テストスイートが CI で 100% 通り、マージ後の退行 19 件はすべて修正済みと記事は述べる。
- 社内ツール（Python から TypeScript）: 約 16.5 万行を週末に移植した。数百のエージェント、8 つのフェーズゲート、3 回の敵対的レビュー、全コマンド出力を元の Python と突き合わせる最終の同等性確認を使った。

## 前提: judge（判定役）を作る

移行が正しいかを決める基準を、最初に機械で動く形にする。

1. Claude でテストを分類する。外部から呼ぶ形のテストと、内部実装に依存するテストを分ける。
1. 外部呼び出し型のテストを、元実装と移植先の両方に対して動くアサーションへ書き直す。敵対的エージェントに、アサーションが弱められていないかを確認させる。
1. judge 自体を検証する。元実装では通り、意図的に壊したコードでは落ちることを確かめる。

Bun は既存の TypeScript テストスイートがあった。もう一方は、実在のシナリオ 7 件を使う同等性ハーネスを新たに作った。既存テストがない場合は、先に judge を作る必要がある。

## 1. ルールブック、依存関係マップ、ギャップ一覧

- ルールブック: 移行後も元の構造を保つか、再設計するかを先に決める。構造を保つなら、型とイディオムの対応表を作る（Bun）。再設計なら設計文書を書く。Bun のルールブックは Claude との対話で作り、8 つのサブエージェントが典型的な失敗の分類ごとにレビューした。
- 依存関係マップ: 明示的なマニフェストがあれば使える。レガシーコードや C/C++/Python のように無い場合は、依存関係を発見する必要がある。Claude Code のエージェントが決定的なスクリプトを作って実行し、マップを出力する。作成はレビューと修正のループの中で行う。マップは、作業の流れの順序づけと、ファイルのバッチ分けに使う。
- ギャップ一覧: 移行先が要求し、元にはなかったものを洗い出す。例は、Zig の手動メモリ管理と Rust の所有権、Python の暗黙のダックタイピングと TypeScript の明示的なインターフェースである。Bun は先に一覧を書き、もう一方は先に翻訳してから監査した。
- ルールブックを先に作り、ルールブックとギャップ一覧を合同で監査する。

## 2. ルールを負荷試験する

- 全ファイルへ展開する前に、小さな移行を試す。Bun は 3 ファイルを 3 通りに処理した。1 つ目はルールブックどおり、2 つ目は「経験豊富なエンジニアとして」翻訳し、3 つ目はその差分から新しいルールを書いた。1,448 ファイルへ展開する前に、重大な問題 2 件が見つかった。
- この方法は、構造を保つ移行にだけ使える。再設計では、設計文書を敵対的レビュアーに攻撃させ、使い捨ての端から端までの実行で検証する。
- 負荷試験の出力はすべて捨てる。目的はルールの改善である。

## 3. 全体を翻訳する

実装、レビュー、修正のループを全ファイルに回す。

- 実装の大量展開は小さいモデル、レビューは大きいモデルに任せる。もう一方の移行は、12 のサブエージェントに Sonnet を使った。
- 作業キューは機械的にする。バッチスクリプトは、翻訳結果がディスクにあるファイルを完了とみなす。これで移行が途中から再開できる。
- 翻訳側は、自信のない箇所に `TODO(port)` を付け、後続の工程に回す。
- 敵対的レビュアーは別々の文脈で 2 つ動かし、意見が割れたら 3 つ目のエージェントが判定する。
- 同じ指摘が繰り返されたら、コードを手で直さず、ルールブックにルールを足して影響したバッチを再生成する。
- コンパイラの置き場所はプロジェクトによる。TypeScript は 1 単位が数秒なので毎回のループに入れた。Rust は cargo に数分かかるため、Bun はこの段階では使わなかった。

## 4. コンパイルを通す

- 段階 3 に統合する場合もある。Bun は、オーケストレーターがワークスペース全体でコンパイラを 1 回呼び、修正エージェントがエラー一覧を並列に処理し、敵対的レビューを付けた。
- Rust 側で数千のモジュールエラーが出た。Zig の遅延コンパイルが許していた循環 import が原因だった。依存を削除する、移す、再構成するのどれにするかを分類するロジックで対処した。
- 人は、エラーの分類結果を見て、構造的な問題がないかを確認する。

## 5. スモークテスト

- クラッシュを作業キューにする。原因ごとにまとめ、グループごとに敵対的サブエージェントがレビューする。

## 6. 振る舞いを一致させる

- 翻訳したコードをシャードに分けてテストを実行する。修正エージェントは、失敗を元と新の両方のコードと照らして直し、敵対的レビュアーがその修正を確認する。
- バイナリを再ビルドできるのはビルド用デーモンだけにする。修正エージェントはパッチを書き、デーモンがまとめて 1 回ビルドし、影響するテストを再実行して結果を返す。
- 多数のテストで同じ失敗が出るなら、上流のルールを直し、そのルールが触れたファイルだけを再生成する。
- テストスイートがない場合: Claude にスクリプトを作らせ、元の Python と移植版で 7 つのシナリオを実行して出力を比較し、全部通るまで回した。その後、Claude に端から端までのテスト一式を設計させ、4 晩連続で自律的に実行した。シナリオ一覧が見逃した問題が見つかった。

## 人が判断する箇所

記事の内容から整理すると、人が関わるのは次のとおり。

- 構造を保つか、再設計するかの方針
- ルールブックの作成と、曖昧な領域の方針決定
- ギャップ一覧と、合同監査
- 負荷試験の結果の確認とルールの改善
- コンパイルエラーの分類に出る、構造的な問題の確認
- フェーズゲート（もう一方の移行は 8 つ）
- ループ中に繰り返し出るパターンへの注意

人の労力は、ルールブックと負荷試験に前倒しする。個々の失敗は修正エージェントに任せ、人はパターンを見る。

## 運用上の原則

- 移行ごとに、先に Claude と計画を立てる。手順はそのまま使わず、出発点として扱う。
- レビューは敵対的に、検証は機械的に行う。コンパイラ、差分、テストを審判にする。
- 高頻度の実装は小さいモデルに任せ、最大のモデルはレビューと、他のエージェントが従うルールの作成に使う。
- キューは機械的で再開可能にする（完了とは出力ファイルが存在すること）。
