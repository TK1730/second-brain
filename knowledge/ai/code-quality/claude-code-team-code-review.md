# Claude Code チームのコードレビューを 7 層で設計する

Claude Code チームが、AI の書くコードの増加に合わせてレビューの仕組みを組み直した方法をまとめる。
内容は Anthropic のブログ記事（2026-10-15 公開）[^claude-article] の要約である。数値はすべて Anthropic が自社の内部運用について述べたもので、第三者の検証はない。

## 問題と考え方

- Claude Code のコードの約 90% を Claude が書いており、レビューの量が非常に多い。Anthropic のモノレポの変更は、5 月の 1 日約 2,500 件から、9 月には 3 万件超になった。行ごとの手作業のレビューはこの量では難しい。
- 「人が読んだか」は不正確な代理指標だと考える。代わりに、変更で何が壊れ得るか、どの検査（自動か人か）が止めるべきかを問う。目標は、差し戻しや障害を増やさずに、人のレビュー時間を最小にすることである。

## 7 つの層

1. 開発中に検証する: Claude がテスト、ビルド、リンター、スクリーンショット比較を実行して結果を示す。別のサブエージェントが新しい文脈で差分を見る。繰り返し出る指摘は、スキル、リント規則、`CLAUDE.md`、`REVIEW.md` に反映して根本で直す。
1. 全 PR に AI レビュー: 複数のエージェントが並行してバグを探し、別の一団が各指摘に投票し、通ったものだけを「重要」「軽微」「既存の問題」に分けて投稿する。指摘は、直すか、理由つきで解決する。
1. セキュリティ指摘でマージを止める: バグやセキュリティの指摘が未解決なら、マージできない。
1. 必須の CI: リント、型、複数環境のテスト、ビルド。PR テンプレートでテストの内容と巻き戻しの計画を問う。
1. リスクに応じた人の承認: 作成者ではなく変更の内容から分類器が段階を決める。
1. マージキュー、フラグ、段階リリース: キューで最新の main に対して再検査する。機能は社内、次に `latest` チャネル、最後に `stable` の順で出す。
1. 早い検知と巻き戻し: フラグはデプロイなしで切れる。週替わりの当番と障害の振り返りで、どの層が止めるべきだったかを問う。

## リスク別の人の承認

| リスク | 例                                                                     | 人の承認                     |
| :----- | :--------------------------------------------------------------------- | :--------------------------- |
| 低     | 文書、文言、社内向け機能、フラグの裏の追加的な変更                     | 自動検査が通れば不要         |
| 中     | 通常のプロダクト変更、キャッシュ、自動更新、システムプロンプトなど慎重な領域 | 1 人                         |
| 高     | 最も危険なコード、常に 2 人が必要な箇所                                | 2 人                         |

- 軽い経路を使えるのは、信頼された作成者だけである。
- エージェントの承認は、人の承認に数えない。エージェントが書いた変更では、指示を出した人が必須のレビュアーになる。
- 承認は特定のコミットに対するもので、コミットが増えたら取り直す。

## レビュアーの改善

- 過去の障害と巻き戻しを評価用の集合にし、コードを知る技術者が確認したうえで、毎日レビュアーを採点する。
- ノイズは、作者の反応（修正、却下、意図的、無視）と、問題のない既知の PR での挙動で測る。
- 収束させる工夫: ラウンドは最大 3 回、数回目以降は差分だけを再レビュー、1 行ごとでなく問題の種類で指摘、同じ指摘を繰り返さない。

人が担うのは、作るかどうかの判断、危険なコード（課金、自動更新、CI の設定）、設計、証拠の読み取り、結果への責任である。

## 記事の数値（自己申告）

- Claude Code への PR のマージ数は 6 月から 9 月で 2 倍超になり、巻き戻された割合は 40% 超減った。基準となる数字は記事にない。
- 実質的なレビューコメントが付いた社内 PR は、リサーチプレビュー開始後に 16% から 54% になった。
- 1 回のレビューと修正で通る PR は 65% から 78%、5 回以上かかる PR は 8.9% から 1.5%、通るまでの平均レビュー回数は 2.08 から 1.32 になった。
- レビュアーが繰り返し指摘したコードの約 59% は、最初のレビューの時点で既に存在していた。
- 1,000 行を超える PR の多くで指摘が出る一方、小さな PR の多くは指摘なしで返る。

## 他のチームへの勧め

- 短い `CLAUDE.md` と `REVIEW.md` から始める。
- テスト、リスク、巻き戻しの欄がある PR テンプレートを作る。
- CI とレビュー指摘の解決を必須にし、レビューのラウンドに上限を置く。
- 承認をリスクで分け、マージキューとフラグを使い、障害を評価用の集合に変える。
- 成功は、1 変更あたりの人の時間の減少で測り、巻き戻しと障害の率を歯止めの指標にする。

## 限界

- 社内の専用ツール、信頼された作成者の一覧、専任のチームを前提にしている。
- 巻き戻しや障害が増えたら承認を自動で厳しくする仕組みは、まだない。
- ノイズ、収束、人なしでマージしてよい低リスクの範囲は、著者も未解決としている。
- フィルタの A/B テストや、検証の手段を与えると結果が 2〜3 倍良くなるという見積もりは、データが示されていない。記事は Code Review などの自社製品の宣伝も兼ねている。
