# Opus 5.5 をナレッジワークの日常モデルとして使う

調査、分析、執筆、メモ・レポート・スプレッドシート・スライドの作成といったナレッジワークで、Claude Opus 5.5 を既定のモデルにするときの指針をまとめる。
内容は Anthropic の記事「Using Claude Opus 5.5 as your daily driver for knowledge work」（2026-11-12 公開）[^claude-article] の要約である。
数値や価格は公開時点のもので、変わりうる。

## モデルの使い分け

判断を要するナレッジワークの大半は Opus 5.5 から始める。
結果に満足できないときは、次の順で手を打つ。

1. 文脈（ファイル、目的、完成の姿）が足りているか確かめる。
1. effort を上げる。
1. それでも誤るならモデルを上げる。

| モデル     | 向く作業                                                 | 価格（入力 / 出力、100 万トークン） |
| :--------- | :------------------------------------------------------- | :---------------------------------- |
| Haiku 5.5  | 簡単な検索、仕分け、要約など短く範囲の狭い大量処理       | $0.10 / $0.50                       |
| Sonnet 5.5 | 指示が明確な作業（メモの清書、テンプレートでのデッキ作成） | $2 / $10                            |
| Opus 5.5   | 調査、財務分析、判断を伴う完成品の文書・デッキ・表       | $4 / $20                            |
| Fable 5.2  | 最も難しい推論や長時間の作業（深い多段階調査など）       | $8 / $40                            |

- Haiku 5.5 の価格は 100k トークンまでのプロンプトに適用される。それより長いと $0.50 / $2.50 である。
- Sonnet を高い effort（Extra high、Max）で使い続けると、タスク単価が Opus 5.5 に近づく。その場合は Opus への切り替えを検討する。
- 価格の高いモデルほど、Pro、Max、Ultra、Team プランの利用枠を速く消費する。

## Opus 5.5 の強み

- 指示に正確に従い、範囲外に広がらない。出力の文書・表・スライドは、編集がほとんど要らないことが多い。
- 数字と出典の扱いが慎重である。記事の社内テストでは、保存された Web スナップショットだけから四半期業績レポートを作る課題で、捏造が 1 つでもあれば不合格とする採点により、18 件中 16 件が合格した。
- 文章が明確である。重要な情報を先頭に置き、与えた文章ルールに従う。長い作業では、何をしたか、何がわかったか、何が必要かを示す。
- 密な開示資料、財務モデル、グラフを正確に読み、案件全体の文脈を保つ。
- 画像の理解が強く、グラフ、スクリーンショット、図表を正確に読む。

## まず試す作業

- アウトラインではなく、完成したスプレッドシートや文書を頼む。
- 長い計画、報告、デッキを渡し、誤りや矛盾（グラフが元データと合わないなど）を探させる。
- 正解のない調査の問いを投げ、資料を集めてメモ・レポート・デッキにまとめさせる。
- UI のプロトタイプ、Web サイト、概念の図解など視覚的な作業を頼む。

## 依頼の仕方を見直す

- **ファイルとシステムをつなぐ**: コネクタで Claude が自分のファイルやシステムに直接アクセスできるようにする。貼り付けだけに頼らない。Team と Enterprise では、オーナーが先にコネクタを有効にする。
- **最初のメッセージで完成の姿を伝える**: ゴール、完成物の形、いつ止まって確認を求めるかを示す。指示を 1 つずつ小出しにしない。
- **「よく考えて」を書かない**: Opus 5.5 は思考が常時オンで、依頼内容と effort から思考量を決める。記事の社内テストでは、この種の文言を消すと応答が早く始まり、品質の低下は見られなかった。
- **Medium effort から始める**: Medium が既定である。記事の評価では、Opus 5.5 の Medium が Opus 5 の High に並ぶか上回った。High は思考が長くコストも増えるが、必ずしも良くならない。Medium で行き詰まったときだけ High にする。設定は、送信ボタンの横のモデル名から Effort を選ぶ。
- **グラフは画像のまま渡す**: 数値を手で書き起こさず、グラフ、スクリーンショット、図を添付する。以前のモデル向けの書き起こしの回避策は不要になっている可能性がある。
- **避けたいスタイルを名指しする**: 「ありきたりにしない」のような一般論では別の定番に置き換わりやすい。避けたいパターン（クリーム色の背景、ピル型ボタンなど）を具体的に挙げる。
- **自社のスタイルを与える**: ブランドガイドや文章ガイドラインを貼るか、コネクタ経由で届く最良の既存デッキを示して合わせさせる。完全に合うまで数回のやり取りが要ることがある。

## 依頼の例

売上の伸びが鈍化した小売企業の分析を題材にした記事の例では、依頼は次の形だった。

- 状況（今年、成長が大きく鈍化した）と、上司のメモにある 4 つの仮説を伝える。
- 手元の資料をすべてフォルダにアップロードしておく。
- 「4 つの仮説をデータと照合し、どれが成立するか教えてほしい」と、ゴールと最終成果物の形だけを示す。
- どのファイルでどの仮説を検証するかは指定しない。

結果として Claude は、4 つの仮説がデータで支持されないことを示し、誰も挙げていなかった説明（新店舗が近くの既存店の売上を奪っていた）を距離の回帰分析で裏づけた。
その分析を、スライダーなどの対話要素を含む文書にまとめ、結論から始める取締役会向けスライドへも変換した。
文書は Word、PDF、Google Docs へ、デッキは PowerPoint、PDF、Google Slides へ書き出せる。

## 自分の仕事で試す

1. 普段は複数回の依頼に分けている作業（調査メモ、差異分析、既存文書からのデッキ作成など）を選ぶ。
1. ファイルと完成品の説明を 1 通のメッセージにまとめ、effort は Medium のままにする。
1. 普段使っている他のモデルの結果と比べる。
