# Opus 5.5 で長いコーディングセッションのコストを抑える

コーディングセッションが長く、文脈が大きくなる傾向を受けた Claude Opus 5.5 の価格とキャッシュの設計、およびそれを生かす運用の要点をまとめる。
内容は Anthropic の記事（Michael Segner 著、2026-09-24 公開）[^claude-article] の要約である。記事の数値は Anthropic 自身の集計や見積もりで、第三者の検証は示されていない。

## 価格と削減幅

- 入力と出力のトークン価格は 20% 下がった。
- キャッシュ読み取りの価格は 60% 下がった。記事は、エージェント型やコーディングの費用の大半をキャッシュ読み取りが占めるとする。
- Anthropic の見積もりでは、トークン課金の典型的な作業負荷で、Opus 5 より約 40% 安くなる。「典型的」という前提で、保証ではない。
- 記事は、公開時点でのキャッシュ済みトークンの単価が他社モデルの約 5 分の 1 だと述べる。比較対象と指標は示されていない。
- 適用はトークン課金の利用である。サブスクリプションの価格に関する記載はない。

## 使われ方の変化（Anthropic の集計）

2026 年 3 月から 9 月の Claude Code の傾向として、記事は次を挙げる。いずれも自社集計である。

- 1 回のプロンプトで Claude が作業する時間は約 3.3 倍になった。
- プロンプトあたりのモデル呼び出しは 40% 超増えた。
- 中断は 68% 減った。セッションあたりのプロンプト数は変わらない。
- リクエストあたりの文脈は 2.6 倍になり、入力と出力のトークン比は 189:1 から 324:1 に上がった。
- ツールサーバーやスキルを使う開発者は約 2 倍に増え、プロンプトへの貼り付けは約 3 分の 1 減った。

大きく自由度の高い作業ほど、再読込される文脈が請求の大半を占めるため、キャッシュ読み取りの値下げが効く。

## 安くなる 3 つの理由

1. 価格: キャッシュ読み取りの 60% 値下げが、長いセッションで最も大きい。
1. Claude Code 側のキャッシュ活用: キャッシュに当たらない入力が半分以上減った。ログイン更新、会話途中の指示追加、ツールのオンデマンド読み込みなど、キャッシュを壊す操作を減らした。
   - Opus 5.5 と Fable 5.1 では、キャッシュを失わずにセッション途中で effort（推論の強さ）を切り替えられる。
   - API キーとクラウドプロバイダーの利用者も、1 時間のキャッシュ有効期間を設定できる（サブスクリプションでは従来から可能）。
   - 分岐したサブエージェントは、同じ文脈を再処理せず、親のキャッシュから始まる。
1. モデルの挙動: 少ないターンで終わる。Zeta Labs は、Opus 5 より 1 タスクあたりのターンとツール呼び出しが減り、費用が約半分で、最難関タスクの完了数が 2 倍になったと報告している。これは 1 社の報告である。
   - 範囲が明確なタスクでは、2 つのモデルのターン数はほぼ同じで、効果は主に値下げ分になる。差が大きいのは、誤った方針で何ターンも進みうる自由度の高いタスクである。
   - 出力の生成は Opus 5 より 30% 超速い。キャッシュ命中率やトークン数は変わらず、無人の長時間実行での待ちを減らす。
   - 記事は、効果はコードベースで変わるため自分で測るよう勧める。

## 実践すること

- Claude Code の `/usage` で、使用量に占めるキャッシュ読み取りの割合を確認する。
- モデルはセッション開始時に決め、途中で切り替えない。キャッシュが壊れる。
- 席を離れる前に compact する。離れた後ではなく前に行う。
- API キーやクラウドプロバイダーで長いセッションを走らせるなら、1 時間のキャッシュ有効期間を使う。
- 文脈は必要なものだけにする。記事は文脈エンジニアリングの別ガイドを案内している。
- Opus 5.5 は、自由度が高く文脈が重い作業に向ける。単純な機械作業では主に値下げ分の効果になる。
