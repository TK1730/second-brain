# コンテキストエンジニアリング: メモリ・コンパクション・ツール結果のクリア

長く動くエージェントでは、ツールの結果・モデルの推論・ユーザーの発言がコンテキストに溜まり続ける。
この記事は、それを抑える 3 つの手段（コンパクション、ツール結果のクリア、メモリ）が、それぞれコンテキストの問題のどの部分を解くのかを、調査エージェントでの実験を通して説明する。
結論は「3 つすべてを使うべきか」ではなく「自分のワークロードがどの問題を抱えているか」から選ぶ、である。

- 出典: [Context engineering: memory, compaction, and tool clearing](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools)（Claude Cookbook）

## なぜコンテキストを抑えるのか

- コンテキストのトークンが増えるほど、モデルがその中の情報を正確に思い出す力は落ちる（context rot、コンテキストの劣化）。
  上限に達する前から、1 トークンあたりの効き目は下がっている。
- 上限が 200K のモデルでは、上限を超えた時点で API が次のリクエストを拒み、作業が途中で止まる。
- 上限が 1M のモデルでは止まらないが、古いツール結果に埋もれて想起が落ちる。
  プレフィル（入力の処理）の遅延もコンテキストの長さに比例する。
- つまり、上限が大きくても、作業中に持つ量（working set）を小さく保つ価値は変わらない。

## 3 つの手段

| 手段               | 対象                               | 失うもの                                         | 解く問題                     |
| ------------------ | ---------------------------------- | ------------------------------------------------ | ---------------------------- |
| コンパクション     | 今のウィンドウの会話全体           | 逐語の細部（要約に圧縮され、細かな数値は落ちる） | セッション内のあらゆる増加   |
| ツール結果のクリア | 今のウィンドウのツール結果だけ     | 古いツール結果（必要なら再取得する）             | ツール結果の肥大             |
| メモリ             | ウィンドウの外のストレージ（永続） | ツール呼び出しのオーバーヘッド                   | セッションをまたいだ引き継ぎ |

- コンパクションとクリアはセッションの中の問題を解き、メモリはセッションをまたぐ問題を解く。
  対象が違うので、競合せずに組み合わせられる。
- 3 つとも Claude API に公式の実装がある。

| API                | 識別子                     | ベータヘッダー                  | 発動のきっかけ                     | 主な設定                                                                            |
| ------------------ | -------------------------- | ------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------- |
| コンパクション     | `compact_20260112`         | `compact-2026-01-12`            | トークン数のしきい値（サーバー側） | `trigger`（既定 150K、最小 50K）、`instructions`、`pause_after_compaction`          |
| ツール結果のクリア | `clear_tool_uses_20250919` | `context-management-2025-06-27` | トークン数のしきい値（サーバー側） | `trigger`（既定 100K）、`keep`（既定 3）、`clear_at_least`、`exclude_tools`         |
| メモリツール       | `memory_20250818`          | 不要                            | モデル自身（ツール呼び出し）       | クライアントが `view`・`create`・`str_replace`・`insert`・`delete`・`rename` を実装 |

## コンパクション

会話が上限に近づいたら、内容を要約し、その要約から会話を再開する。

- 会話全体（ユーザーの発言、推論、ツールの呼び出しと結果、前回の要約）をまとめて 1 つの要約にする。
- 要約には推論のコストがかかるが、ツール結果以外の増加（対話や推論）も扱える。
- 実験では、課題の中心となる事実（寿命の数値、生物の名前、主な比較）は要約に残り、付録の表の 1 セルのような細部は落ちた。
  クリアが結果を丸ごと消すのに対し、コンパクションは中身を圧縮して残すが、逐語の細部を失う。
- API では、発動すると `compaction` ブロックが返る。
  次のリクエストでは `{"type": "compaction", "content": block.content}` として送り返し、API はそれより前の会話を捨てる。

```python
context_management={
    "edits": [{
        "type": "compact_20260112",
        "trigger": {"type": "input_tokens", "value": 150_000},
        "instructions": (
            "Summarize this research agent transcript. Preserve every "
            "quantitative lifespan figure and effect size with its "
            "source organism, and note which documents have been read "
            "and which remain. Wrap the summary in <summary></summary>."
        ),
    }]
}
```

- `instructions` は既定の要約プロンプトに足されるのではなく、置き換える。
  渡すなら、要約の目的や `<summary></summary>` で囲む指示まで自分で書く。
- 落としたくない細部（上の例では数値と、読んだ文書・残りの文書）を名指しで書くとよい。

## ツール結果のクリア

古い `tool_result` ブロックの中身を短いプレースホルダに置き換える。
`tool_use` ブロックは残すので、モデルは「どの入力でツールを呼んだか」を覚えている。

- 会話の一部だけを機械的に書き換えるので、推論のコストがかからず、3 つの中で最も安い。
- ファイルの読み込みや API の応答のように再取得できる結果に向く。
  必要になればツールをもう一度呼べばよい。
- 失うもの: 最近の `keep` 件より前のツール結果。
  エージェントのメモが薄いと、まとめの段階で細部が欠けるか、同じファイルを読み直すことになる。
  ローカルファイルの再読み込みはほぼ無料だが、遅い API やレート制限のある API では高くつく。
- 発動すると、レスポンスの `context_management.applied_edits` に、消したツール呼び出しの数と空いたトークン数が出る。
- 拡張思考のブロックには `clear_thinking_20251015` がある。
  両方を使うときは、`edits` 配列の先頭に置く。

```python
context_management={
    "edits": [{
        "type": "clear_tool_uses_20250919",
        "trigger": {"type": "input_tokens", "value": 30_000},
        "keep": {"type": "tool_uses", "value": 4},
        "clear_at_least": {"type": "input_tokens", "value": 10_000},
    }]
}
```

- クリアはプロンプトキャッシュの接頭辞を無効にする。
  `clear_at_least` で一度に十分な量を消し、キャッシュの書き直しに見合うようにする。
- `trigger` と `keep` の適値は、ツール結果の大きさ、見直す頻度、再取得の安さで変わる。
  `applied_edits` を見ながら、いくつかの設定を自分のワークロードで試す。

## メモリツール

エージェントがウィンドウの外のファイルにメモを書き、後で必要な分だけ読み戻す（just-in-time retrieval、必要なときに取り出す）。
コンパクションとクリアは今のコンテキストにしか効かず、新しいセッションが空のウィンドウで始まる問題は解けない。
メモリはその問題を解く。

- クライアント側のツールである。
  API はツールの約束ごとと、「何よりも先にメモリのディレクトリを見る」というシステムプロンプトを自動で注入し、保存先はアプリ側が実装する。
- 何をいつ保存するかはモデルが推論の中で決める。
- 実装では、`../` によるパストラバーサルを防ぎ、ファイルの大きさとディレクトリ全体の大きさに上限を設ける。
- 実験では、メモリのある 2 回目のセッションは、1 回目の結果を読んでから作業し、元の文書を読み直さずにまとめを書けた。
  メモリのない 2 回目は、同じ事実を一から調べ直した。
- 失うもの: 読み書きのたびのツール呼び出し。
  セッション内のコンテキストの増加には効かない。
  保存の中身はエージェントの判断の質に左右される。

保存の中身を良くする指示の例:

- 話題を絞る: 「`<topic>` に関係する情報だけをメモリに書く」。
- 整理させる: 「メモリのフォルダを編集するときは、内容を最新で一貫した整理された状態に保つ。不要になったファイルは名前を変えるか削除する。必要がなければ新しいファイルを作らない」。
- 初期化セッションを設ける: 本作業の前に、進捗ログや機能のチェックリストなどの枠を作るセッションを 1 回走らせ、後のセッションはそれを読んで状態を取り戻す。
- 保存先を手入れする: ファイルの大きさを追い、長く読まれていないファイルを片付ける。

## 組み合わせる

- Claude Code は、コンパクションと 2 種類のメモリを併用している。
  人が書いてリポジトリに入れる `CLAUDE.md`（規約・構成・手順）と、Claude 自身が書く auto memory（ビルドコマンド、デバッグの知見、指摘から学んだ好み）である。
- クリアとメモリツールを併用するときは、`exclude_tools: ["memory"]` を設定する。
  設定しないと、メモリの読み書きの結果まで消え、エージェントが保存したばかりの内容を見失う。
- 3 つを同時に動かすと、それぞれが自分の役目の場面で発動する。
  ただし役割を分けさせるにはしきい値の調整が要り、つまみと相互作用も増える。

## 使わない方がよい場面

- メモリを使わない: 毎回まっさらに始めたいとき（会話ごとに独立したチャットボットなど）。
- コンパクションを使わない: セッションが上限より十分短いとき。
  要約は細部を失うので、余裕が要らないなら失うだけになる。
- クリアを使わない: 過去のツール結果を全文で見比べ続ける必要があるとき（複数文書の段落を並べて比べる分析など）。
  消すと読み直しが増える。

## ワークロードから選ぶ

記事は次の表を「答えではなく、試す仮説」として示している。

| ワークロードの特徴                                     | まず試す                 | 注意すること                                     |
| ------------------------------------------------------ | ------------------------ | ------------------------------------------------ |
| 何日・何週にもまたがるセッション                       | メモリツール             | ツール呼び出しの負担、事実が変わったときの古さ   |
| セッションをまたいでユーザーの好みを学ばせたい         | メモリツール             | 個人情報の扱い、好みが変わったときの古さ         |
| 大きく、再取得できるツール結果                         | クリア                   | 消した直後の読み直し（`keep` と trigger を調整） |
| 対話が主なコンテキスト                                 | コンパクション           | 細かな数値が要約で落ちること                     |
| 再取得しにくいツール結果（一時的な API、アップロード） | クリアよりコンパクション | その結果が要約に正しく残るか                     |
| 毎回まっさらに始めたい                                 | メモリを使わない         | 望まない状態の持ち越し                           |
| セッションが上限より十分短い                           | コンパクションを使わない | 要らない情報の欠落                               |

## 実験から得た教訓

- 損失の大きさは連続的に違う。
  クリアはツールが呼び直せる限り損失がない。
  コンパクションは要約のプロンプトが決める範囲で損失がある。
  メモリは保存したものには損失がないが、何を保存するかの判断次第である。
- 重ねるほど対応できる範囲は広がるが、同じだけ複雑になる。
  足す前に、その手段が自分のワークロードのどの問題を解くのかを問う。
- 設定の良し悪しは、コンテキストの推移・発動イベント・ツールの呼び出し回数を記録するテスト用のハーネスで比べる。
- ツール結果の肥大には、別の手段もある。
  プログラムからのツール呼び出し（Programmatic tool calling）は大きな結果をそもそもコンテキストに入れず、ツール検索（Tool search）はツール定義の肥大を減らす。
