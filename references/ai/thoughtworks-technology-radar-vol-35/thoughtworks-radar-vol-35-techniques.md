# Thoughtworks Technology Radar Vol.35: Techniques

Thoughtworks Technology Radar Vol.35 (2026 年 11 月) の Techniques (手法) 象限の要約である。
45 項目のほとんどが AI エージェントを使った開発と、そのハーネスやコンテキストの扱いに関するものである。
リングの意味と今号のテーマは [全体像の文書](/references/ai/thoughtworks-technology-radar-vol-35/thoughtworks-radar-vol-35-overview.md) を参照する。

- 出典: Thoughtworks Technology Radar Volume 35 (PDF)、[thoughtworks.com/radar](https://www.thoughtworks.com/radar)

[TOC]

## Adopt

### 1. Agent sandboxing

- エージェントを、権限と外部システムへのアクセスを絞った隔離環境で動かす。
  コーディングに限らず、業務システムで動くエージェントも含めて既定にすべき手法とした。
- 万能の方法はないので、エージェントと周辺システムの脅威モデリングに基づき、リスクに応じて隔離の度合いを決める。最小権限の原則を守る。

### 2. Mutation testing

- コードに小さな人工的なバグを入れ、少なくとも 1 つのテストが失敗するかを確かめて、テストの質を測る。
- AI が生成したテストは、中身の薄いテストでカバレッジだけを上げやすい。ミューテーションテストはそれを見抜くガードレールになる。
- エージェント自身がループの中でコードを書き換えてテストを回すこともできる。時間がかかるので、対象パッケージを絞るか、最近変えたコードだけに対して実行する。

### 3. Path-to-production mapping

- 開発者の端末から本番までの工程をホワイトボードに書き出し、次に各工程の痛みを書き込むワークショップである。設計・開発・リリース・運用の関係者全員で行う。
- エージェントでコードの量が増えると、コーディング以外の工程のボトルネックが表に出る。コーディング速度ではなく、端から端までの流れを最適化するために使う。

### 4. Post-quantum cryptography

- 将来の量子計算機による攻撃に耐える暗号方式である。今暗号化したデータを集めて後で解読される恐れがあるため、鍵交換の移行が最も急ぐ。
- NIST の標準 (ML-KEM、ML-DSA、SLH-DSA) は確定済みで、各国は 2030〜2035 年の移行を目標にしている。
- Java (JDK 24 以降) など、言語や基盤の新しい版が対応し始めている。新規開発では必須にし、既存システムは移行計画を早める。

### 5. Progressive context disclosure

- LLM に最初は必要最小限のコンテキストだけを渡し、応答や利用者の入力をきっかけに追加の情報を読み込ませる手法である。
- 例: AGENTS.md を短く保って詳細な文書へのリンクを置く、MCP ツールやエージェントスキルの中身を使うときまで読み込まない、利用者の入力に応じて RAG で情報を取ってくる。
- トークンの消費と費用を減らし、コンテキストの劣化 (context rot) を防ぐ。本格的なアプリケーションではほぼ普遍的になったため Adopt に移った。

### 6. Threat modeling

- システムへの脅威を洗い出す演習で、プロンプトインジェクションや自律的な行動など、生成 AI 特有のリスクを見つけるのに欠かせない。
- 人が主導し、エージェントが支援する形で、開発サイクルの中で定期的に行う。
- 既知の脅威から始めて自分の文脈に当てはめる。MITRE ATLAS、MAESTRO、STRIDE、toxic flow analysis が役立つ。
- 最後に、モデルの非決定的な振る舞いを許す場所、許さない場所、決定的なガードレールが要る場所を明示的に決める。

## Trial

### 7. Agent plugin marketplace

- スキル、指示、MCP サーバー、サブエージェント定義などのハーネス資産を組織内に配布する仕組みである。リポジトリ間でコピーすると、公開・発見・更新ができない。
- Thoughtworks では、文書化した Git リポジトリに Agent Plugins 形式のプラグインを置き、Agent Package Manager で依存として管理している。Claude Code のプラグインマーケットプレイスがこの形を広めた。

### 8. Agent-maintained knowledge bases

- チームの共有知識をリンクしたプレーンテキストのファイル (Obsidian の vault など) に置き、コーディングエージェントに保守させる。
- Andrej Karpathy の LLM Wiki がこの形を説明している: エージェントが読むが変えない原資料、エージェントが保守する wiki、保守の仕方を導くスキーマの 3 つで構成する。
- 個人の「第二の脳」から始める人が多いが、チームで共有する段階に進むことを勧めている。
- 生成された知識は現実からずれていく。人が定期的に手を入れないと AI-driven documentation sprawl になる。

### 9. Anchoring coding agents to a reference application

- 雛形 (テンプレート) が古くなる問題に対し、構造だけの薄い雛形と、変わり続けるプラットフォームの規約を分ける。
- エージェントは生成時に、OpenWiki や agent-maintained knowledge base などの最新の情報源を参照して規約や設定を取ってくる。雛形の道具を更新し続けなくても、今の標準に沿ったコードを生成できる。

### 10. Coding harness for general-purpose agents

- コーディング以外のエージェント (文書処理、運用支援、移行計画など) を、エージェントフレームワークで一から組まず、成熟したコーディングエージェントの実行環境の上に作る。
- Claude Agent SDK、Codex SDK、OpenCode のサーバーと SDK、Pi の SDK が使える。コンテキストの圧縮、セッションの保存、ヘッドレス実行がすでに備わっている。
- 制御の自由度は下がるが、よく試された実行環境が手に入る。
- 注意点: サンドボックスや承認の仕組みは製品ごとに違う。システムプロンプトや組み込みツールはコードを書く方向に誘導するので、対象の業務に合わせて見直す。トークン消費も監視する。

### 11. Feedback flywheel

- セッションの終わりに「共有の成果物 (AGENTS.md やスキル) を変えるべきか」を問い、チームのふりかえりで何を更新するかを決める。1 人の学びをチーム全体に広げる。
- フィードバックセンサー (失敗し続けるチェック)、agent suggestion box (エージェントが報告する問題)、過去のセッションから編集案を出す道具を材料にする。
- 足すだけでなく削ることも必要である。ルールが溜まるだけだと agent instruction bloat になる。context profiling で読み込む量が増えていないかを確かめる。

### 12. Graph-grounded codebase reasoning

- コード、文書、それらの関係をグラフとして表し、エージェントには関係する部分グラフだけをコンテキストとして渡す。Graphify などの道具がある。
- ただし、find や grep のような単純な道具のほうが成績が良い場合があるという研究もある。どんなときにグラフが効くかを確かめる目的で Trial に置いた。

### 13. Grilling

- 計画を実行に移す前に、コーディングエージェントが人に質問を重ね、曖昧な点を解消する手法である。mattpocock/skills のものが最もよく知られる。
- エージェントが意図を推測で埋めるのを防ぎ、前提を表に出す。人も自分の前提を見直すことになり、計画をよく理解した状態で決定記録に残せる。

### 14. Interactive visual plans with agents

- 図、利用者の流れ、ワイヤーフレームを含む、自己完結した HTML や MDX の計画書をエージェントに作らせ、実装前に一緒に確かめる。長い文章の計画より意図を確かめやすい。
- 大きな事前設計には使わず、小さく確かめられる段階に分けて進める。エージェントが実装する前の、人のレビューの区切りとして使う。

### 15. Managed agents runtime

- 開発者の端末ではなく、実行・インフラ・運用を管理する基盤の上でエージェントを動かす。基盤がエージェントループ、サンドボックス、トリガー、認証情報、セッション状態、可観測性を受け持つ。
- 課題やスケジュールから仕事を拾い、プルリクエストを出す長時間の非同期作業に向く。Claude Managed Agents は汎用の例である。
- 自前の基盤でもよい。いずれの場合も、本番インフラとして扱い、サンドボックスとバージョン管理されたエージェント定義を備える。

### 16. Open-weight models

- 重みや推論コードが公開されたモデル (DeepSeek、GLM、Kimi など) が転換点に達した。複雑な推論やコード生成の本番業務でも良い結果が出ている。
- 費用に加え、配置の自由度、ベンダーロックインの回避、データ主権の強化が利点である。主要クラウドがマネージドで提供し始め、導入の壁も下がった。
- 安い代替としてではなく、コーディング以外も含む幅広い業務で評価すべきである。

### 17. Risk-tiered human oversight

- 変更が壊しうるものに応じて、レビューの深さを変える。すべてを同じ強さで見ると human-in-the-loop theater になる。
- 最も危険で戻しにくい変更は人が適用し、中程度は人がレビューし、低リスクは CI を通してエージェントが自動マージする。
- 判定には、コードベースの特定の場所を要注意とするゾーンと、LLM による変更の分類 (誤ることもある) を組み合わせる。

### 18. Self-improving harness

- エージェントが実行トレースと評価結果を分析し、プロンプト、コンテキスト戦略、ワークフロー、スキル、ツール、メモリなどのハーネスの改善を提案・実施する。
- Meta-Harness や VERSE などの研究がある。可観測性 (失敗を診断できること) とプログラム可能性 (部品を調べて変更し試せること) が前提になる。
- 改善の効果は検証が必要である。回帰テスト付きの範囲を限った実験にし、目的や変えてよい範囲は人が決める。

### 19. Small language models

- 「大きいほど良い」から、良質な学習データ、蒸留、量子化で改善する方向に業界が移っている。
- 要約、構造化データの抽出、ルーティングのための意図分類、簡単なコーディングなど、狭く頻度の高い作業に有効である。
- 多段の推論や確実なツール呼び出しが要らないなら、低コスト・低遅延の選択肢として SLM を検討する。

### 20. Stateful guardrails

- ガードレールを 1 通のメッセージ単位から会話全体に広げる。直近の会話の要約をポリシーに照らして調べ、違反の回数や利用停止の状態をセッションをまたいで持つ。
- 1 通ずつは問題なく見えても、会話全体では回避や脱獄の試みだと分かることがあるためである。
- 毎ターンの評価は遅延と費用を増やし、閾値の調整を誤ると正当な利用者を締め出す。

### 21. Subagents for better context management

- 探索、ツールの出力、やり直し、途中の推論をサブエージェントに任せ、オーケストレーターには短い要約だけを返させる。オーケストレーターのコンテキストを守るためである。
- 目安: 同時に動かすのは 2〜4 個にする。同じコードの理解が要る作業は 1 つのエージェントにまとめる。サブエージェントの全記録を本筋に取り込むと効果が消える。
- 狭い作業には安いモデルを使って費用を下げられる。効果が体系的に測られていないため Trial とし、context profiling で本当にコンテキストが減ったかを確かめることを勧めている。

### 22. Toxic flow analysis for AI

- 非公開データへのアクセス、信頼できない内容への接触、外部との通信の 3 つが揃うと (lethal trifecta)、プロンプトインジェクションやツールの汚染が起きうる。
- システム内の危険なデータの通り道を特定する分析である。役に立つように見えて機密を持ち出す隠れた指示を含むスキルにも注意する。Agent Scan などの道具を使う。

### 23. Unattended overnight agentic builds

- 帰る前にエージェントに機能 1 つ分の仕事を渡し、翌朝に結果を見る。日中は人が計画と仕様を詰め、夜はエージェントにコードを書かせるチームもある。
- 前提条件がある: サンドボックスでの実行、事前に書いた仕様、エージェントが自分の誤りを直せるフィードバックセンサー、行単位のレビューに代わって変更を検証できるハーネス。
- この前提を満たすよう促すこと自体に価値がある。満たしていないチームにとっては、基盤を整える目標になる。

## Assess

### 24. Agent pipeline responsibility

- ビルドを緑に保つ責任にエージェントも加える。ビルドの状態やログをエージェントのツールから見えるようにし、壊れた変更を push させない仕組み (pre-push や サーバー側のゲート) で強制する。
- 人が失敗ログをチャットに貼って中継するだけなら、その人は meat proxy になる。

### 25. Agent suggestion box

- 動いているエージェントが、遭遇した問題 (ツールのバグ、環境に無い依存など) を報告できる場所である。Slack のチャンネル、メモリストア、課題管理のどれでもよい。
- 出力がプルリクエストだけだと、エージェントは問題を黙って回避し、次のセッションも同じ問題に当たる。メモリは壊れた道具を避けさせるだけだが、提案箱は道具を直させる。
- 報告の半分ほどは誤検知だったという例もあり、人のレビューが要る。

### 26. Context profiling

- トークンをどこに使っているか (ファイル読み込みか、MCP のツール呼び出しかなど) を分析する。最適化の前に測るという原則と同じである。
- 大きな節約は、適切な時期にセッションを消す、キャッシュの設定を調整する、ビルドスクリプトの出力を減らすといった単純な変更から生まれることが多い。測らずに圧縮プロキシのような複雑な手段に飛びつかない。

### 27. Enterprise harness

- コーディングエージェントが使うもの (スキル、ツール、社内情報への接続、承認済み技術、ADR、本番までの手引き、フック、セキュリティポリシー) を組織全体で共同管理する層である。開発者体験基盤のエージェント版にあたる。
- 合意された作り方はまだ無い。オープンな標準で共有し、agent plugin marketplace で配り、薄く分散した形に保つ。

### 28. Foundation models for structured data

- Transformer を構造化データに適用し、組織のイベント列や取引ログで事前学習した基盤モデルである。TabPFN や TabFM がある。
- 特徴量設計や再学習を何度もしなくても、軽い微調整で複数の予測タスクに使える。

### 29. Harness quality evaluation

- スキル、プラグイン、AGENTS.md、ガードレールなどのハーネスが本当に効いているかを評価する。
- 非決定的な部分は PluginEval などで評価し、決定的なガードレールにはテストを用意して TDD で作る。評価は夜間や CI で定期的に回す。

### 30. Local coding models

- 以前は Caution だったが、ローカルで動くオープンウェイトモデル (Qwen3.8-27B など) が成熟した。
- コードベースの索引付け、ログの解析と要約、最初のコーディング、差分の自動レビューなど、フロンティアモデルが要らない作業に使える。クラウドのトークン費用を避け、オフラインの予備にもなる。

### 31. MITRE ATLAS

- AI・機械学習システムを狙う攻撃の戦術と手法の知識ベースである。MITRE ATT&CK を補う。
- 共通の語彙が無いとセキュリティのリスクは見落とされたり形だけのチェックになったりする。脅威モデリングの支えとして使う。

### 32. Production-aware coding agents

- コーディングエージェントに、本番の可観測性データや道具への適切なアクセスを与える。変更の計画、デプロイ後の影響の確認、本番の問題調査に役立つ。
- フィードバックの層をコミット前のチェックから本番まで広げる考え方である。

### 33. Programmatic tool calling

- モデルがツールを 1 回ずつ呼ぶのではなく、ツール呼び出しを組み合わせたコードを書き、実行環境で動かして、選んだ結果だけをコンテキストに戻す。
- 名前はまだ揃っていない (Code Mode、programmatic tool calling、code execution with MCP など)。
- Code Mode の MCP サーバーを使うと、クライアント側で操作ごとの承認がしにくくなる。認可と承認はサーバー側で強制する必要がある。

### 34. Semantic review of AI-edited prose

- エージェントは仕様、ADR、計画を人が読むより速く書き換える。テキストの差分では言い換えや書式の変化に意図が埋もれる。
- LLM に意味の変化 (事実の変更、矛盾、受け入れ条件の再定義、範囲の変更) を分析させ、差分に重ねて見せる。文書を編集したときに動くスキルとして実装できる。

### 35. Tests as data over tests as code

- テストケースを YAML や JSON などの構造化データで書き、プロジェクト固有のハーネスがそれを読んで実行する。Gherkin による BDD が代表例である。
- スキーマがエージェントの出力を縛るので、生成もレビューもしやすい。レガシーの移行では、同じテストデータを新旧両方の実装に流して振る舞いの一致を確かめられる。

## Caution

### 36. Agent instruction bloat

- AGENTS.md、スキル、ワークフローなどの指示は時間とともに伸び、長く、矛盾し、古くなる。
- 対策: まず決定的なフックやチェックに変えられる指示を変える。新しいモデルが出るたびに指示を見直し、要らなくなったものを消す (回帰テストではなく進歩テスト)。残りは progressive context disclosure で必要なときだけ読ませる。
- Anthropic は最新モデル向けに Claude Code のシステムプロンプトの 80% 以上を削っても、測れる性能の低下は無かった。

### 37. Agent skill cognitive surrender

- 中身を理解しないまま、大きなコミュニティ製スキル集や重いエージェントフレームワークを丸ごと取り込むアンチパターンである。
- システムの理解を失うだけでなく、レビューしていない指示が実行経路に入るセキュリティリスクや、出所の違うスキル同士の衝突も生む。
- 取り込む前にスキルの指示を読んで確かめる。モデルが賢くなると汎用スキルは不要になりやすいので、プロジェクト固有のスキルを育てるほうが価値が高い。

### 38. AI-accelerated shadow IT

- コードを書かない人もコーディングエージェントでアプリを作るようになった。歓迎すべきことだが、セキュリティの問題と、テスト・デプロイ・可観測性の欠如というリスクがある。
- 熱意を消すのではなく、安全に試せる環境と enterprise harness を用意し、セキュリティには厳しく、役立つ道具には正式な支援への道を用意する。

### 39. AI-driven documentation sprawl

- AI や仕様駆動開発の道具で大量の Markdown を生成すると、品質と進捗があるように見えるが、文書は CI などの品質ゲートを通らないため、古く矛盾した文書が積もる。
- 古い ADR や矛盾した仕様はエージェントのコンテキストを浪費し、誤ったコード生成につながる。
- Markdown を第一級の成果物として扱い、人が意図して刈り込み、まとめ直す。

### 40. Blanket frontier model usage

- LLM を使う作業をすべて、費用・遅延・必要な能力を考えずに最も強いモデルに任せることである。探索、簡単な編集、要約などは小さなモデルやオープンウェイトモデルで足りることが多い。
- 手動、サブエージェントごと、ハーネスの自動切り替えでモデルを変えられる。プロンプトキャッシュはモデルごとなので、新しいセッション、サブエージェント、計画から実装への引き継ぎなどの自然な区切りで切り替える。
- ただし強いモデルのほうが少ないトークンで終わることもあるので、context profiling で効果を確かめる。

### 41. Coding throughput as a measure of productivity

- AI が生成したコードの割合や消費トークン数などの活動量の指標は、導入の度合いは示しても生産性の代わりにはならない。
- DORA 指標や協働の質を使い、改善を事業の成果に結びつける。活動量を目標にするとグッドハートの法則に陥り、目標達成のための無駄な AI 作業を生む。

### 42. Human-in-the-loop theater

- 人が実際には評価できない操作や差分を承認するだけの、形だけの承認である。誰も本当には決定に責任を持たない。
- 人が本当に判断できる変更だけを risk-tiered human oversight で人に回す。残りは、個々の変更を見る代わりに、ミューテーションテスト、プロパティベーステスト、TLA+ や Quint などの形式モデル、エージェントによる意味のレビューでシステムを制御する。

### 43. Meat proxy

- 確かめていない LLM の出力を、読まず、検証せず、判断も加えずに同僚へ転送する人のことである。
- 検証の負担を相手に押しつけ、自分の品質責任を放棄している。human-in-the-loop theater が偽の承認なら、こちらは偽の作者である。

### 44. Naive context compression

- トークン費用を下げるためにプロンプトを圧縮する道具 (Headroom、RTK、Tamp など) を安易に使うことである。
- 問題: プロンプトキャッシュが効かなくなり、かえって請求額が増える。情報が落ちて精度が下がる。圧縮に LLM を使うと遅延と費用が増える。
- 導入前に context profiling で正味の費用と精度を評価する。元データへの参照を残してツール出力を圧縮する道具や、タスクの区切りで一度だけ履歴を刈る道具を選ぶ。

### 45. Stacked pull requests

- 大きな変更を、依存関係のある小さなプルリクエストの列に分ける。レビューの負担と待ち時間を減らせ、GitHub もネイティブに対応した。
- しかし多くの場合、事前の分割の甘さを補う回避策になっている。小さく独立した単位で仕様を決め、分け、届けることが本来の習慣である。
