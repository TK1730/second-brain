## ハーネスエンジニアリングとは

ハーネスエンジニアリングとは、Mitchell Hashimoto 氏が提唱した「AI がミスをするたびに、二度とそのミスをしないよう環境 (ハーネス) 側に恒久的な対策を組み込む」アプローチである。
LLM は本質的にステートレスな関数であり、セッションをまたいで過去の失敗を自発的に学習・記憶し続けることはできない。
そのため、モデルの出力品質を安定させるには、外部から毎回ルール・文脈・制約を注入し、行動の境界を強制する仕組み (ハーネス) が不可欠になる。

記事では、AI を活用するエンジニアリングの段階を以下の 3 つのレイヤーに整理している。

| レイヤー | 焦点 | 役割と具体例 |
| :--- | :--- | :--- |
| プロンプトエンジニアリング | 何を聞くか | 1 回の指示文の書き方や言い回しを工夫し、期待する出力を引き出す。 |
| コンテキストエンジニアリング | 何を見せるか | タスクに必要な背景知識、ドキュメント、コード片を適切な粒度でコンテキストウィンドウに供給する。 |
| ハーネスエンジニアリング | どう動かすか | ルール定義、スキル、サブエージェント分割、ツール権限の制限などを組み合わせ、AI が安全かつ確実に動く外側の環境を構築する。 |

## Claude Code における 5 層の設計パターン

記事では、単一の `CLAUDE.md` にあらゆる指示を詰め込むとコンテキストの肥大化と指示の希薄化を招くという課題に対し、Claude Code の設定機構を以下の 5 層に分離する設計パターンを提案している。

### Layer 1: `CLAUDE.md` (プロジェクトの憲法)

最上位の指示書として、すべてのセッションで常に読み込まれる「プロジェクトの憲法」に位置付ける。
ここにはプロジェクトの全体構造、基本原則、ディレクトリ構成、絶対に守るべき禁止事項など、あらゆる作業に共通する最小限のコア情報だけを記述する。
また、個人の作業環境や好みに依存する設定は `CLAUDE.local.md` などに分離してインポートし、チーム共有の憲法と個人設定を混在させない。

### Layer 2: `Rules` (`.claude/rules/*.md` — ドメイン特化のルールブック)

特定のディレクトリやファイル種別、あるいは特定のタスク領域にのみ適用される命名規則やフォーマット規約は `.claude/rules/*.md` に分離する。
対象のパスや条件に応じてルールを分割管理することで、`CLAUDE.md` の肥大化を防ぎ、作業対象に関連する規約だけを的確に効かせることができる。

### Layer 3: `Skills` (`.claude/skills/*/SKILL.md` — 再利用可能なワークフロー)

定型的な作業手順やスクリプトの実行フローは `.claude/skills/*/SKILL.md` としてパッケージ化する。
常時読み込ませる必要のない専門的な手順をスキルとして切り出すことで、必要なときだけオンデマンドで呼び出し、通常時のコンテキスト消費を節約できる。

### Layer 4: `Agents` (`.claude/agents/*.md` — 専門特化のサブエージェント)

大量のファイル探索、ログ調査、メモ整理など、多くのトークンを消費する作業は `.claude/agents/*.md` で定義した専門のサブエージェントに委譲する。
サブエージェントは独立したコンテキストウィンドウで動作し、要約された結果だけをメインセッションに返すため、メインセッションのコンテキスト圧迫や注意力の低下を防ぐことができる。

### Layer 5: `Settings` (`.claude/settings.json` — 権限とセキュリティの制御)

最下層の安全装置として、`.claude/settings.json` でツールの実行権限やセキュリティ境界を制御する。
実行を許可 (allow) または拒否 (deny) するツールやシェルコマンドを明示的に制限することで、プロンプトの指示だけでは防ぎきれない意図しない破壊的操作をシステムレベルで遮断する。

## 設計と運用で得られた知見

5 層のハーネスを構築・運用するなかで得られた実践的な知見として、以下の 3 点が挙げられている。

- **「何をやるか」以上に「何をやらないか」を明記する**: LLM は良かれと思って頼んでいないファイル整理やスコープ外のリファクタリングを行いがちであるため、勝手なファイル整理やスコープ外の修正の禁止を明文化することが出力の安定に強く効く。
- **決定論的な処理はスクリプトに切り出す**: ファイルの定型変換や集計など、決定論的に処理できる作業を LLM に直接行わせるとミスやトークン浪費が生じるため、それらはスクリプトに切り出し、LLM には判断や要約などの非決定論的な作業だけを担わせる。
- **Hooks は段階的に導入する**: Hooks 機能は自動化に有効である一方、毎回のツール実行にオーバーヘッドや複雑性が生じるため、まずは上記の 5 層の基本構成を固めてから、必要に応じて段階的に導入するのがよい。
