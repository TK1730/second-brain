# エージェントの失敗をどの層で直すか: ハーネス・ループ・グラフの切り分け

`@beamnxw` が X 上で発信している、AI エージェントの失敗原因を「ハーネス (Harness)」「ループ (Loop)」「グラフ (Graph)」の 3 層に切り分けて修正する設計フレームワークの要約である。
なお、個別ポスト ID (`2119806541821776215`) の本文は検索インデックス上で直接取得できないため、本文書では公開されている `@beamnxw` のハーネス・ループ・グラフ設計論および Product Harness の知見を統合して整理している。

- 著者: `@beamnxw`
- 出典: [beamnxw の X 投稿](https://x.com/beamnxw/status/2119806541821776215)

## 概要: プロンプトやモデルのせいにする前に構造を切り分ける

AI エージェントが期待通りに動かないとき、開発者はつい「プロンプトを書き換える」か「より上位のモデルに変える」ことで解決しようとしがちである。
しかし、失敗の根本原因がモデルの外側の構造にある場合、プロンプトをどれだけ調整しても問題は再発する。
`@beamnxw` の設計フレームワークでは、エージェントを取り巻くエンジニアリングを **ハーネス (Harness)**、**ループ (Loop)**、**グラフ (Graph)** の 3 つの層に分解し、起きている症状に応じて「どの層を直すべきか」を明確に切り分ける。

| 層 | 単位と対象 | 主な責務 |
| :--- | :--- | :--- |
| **1. ハーネス層 (Harness)** | 1 回のモデル呼び出しの境界 | ツール定義、入出力スキーマ、バリデーション、コンテキスト・役割ファイルの注入。 |
| **2. ループ層 (Loop)** | 単一タスクの反復サイクル | テストや評価器による正否判定と、エラー・差分を添えた自律的な再試行制御。 |
| **3. グラフ層 (Graph)** | 複数タスク・複数役割の状態遷移 | フェーズ分割、エージェント間のルーティング、合意ゲートと引き継ぎの制御。 |

## 1. ハーネス層 (Harness Engineering — 1 回の呼び出しの境界と道具を整える)

### 役割

モデルが安全かつ正確に手足を動かすための「外側の枠組み」である。
利用可能なツールの定義、入出力スキーマの制約、バリデーション、例外処理、および作業に必要なコンテキストや役割定義ファイルの注入を担う。

### ここで直すべき失敗

- ツール呼び出し時の引数のフォーマットエラーや型不一致。
- JSON 等で存在しないキーを出力する、あるいは必須フィールドを欠落させる。
- 1 回のモデル呼び出しにおける入出力のミスマッチや、与えられた役割・スコープからの逸脱。

### 対策

プロンプトで「正しい JSON で出力して」「スコープを守って」と頼むのではなく、スキーマ検証やゲートによって不正な出力をシステム側で物理的に弾く。
また、`@beamnxw` が示すプロダクト開発向けのハーネス構成 (`Product Harness Starter`) では、以下のように役割と状態を構造化ファイルに分離して境界を定義する。

- **プロジェクト・仕様の境界**: `CLAUDE.md` (全体原則)、`PRODUCT.md` (プロダクト定義)、`CONTRACT.md` (フェーズ間の完了合意条件)、`FEATURES.json` (機能一覧と状態)、`HANDOFF.md` (セッション・役割間の引き継ぎ事項)。
- **役割別の境界**: `PLANNER.md` (計画・仕様策定)、`BUILDER.md` (実装)、`EVALUATOR.md` (独立した検証・評価) に指示書を分け、1 つのエージェントにすべての役割を混在させない。

## 2. ループ層 (Loop Engineering — 検証と再試行のサイクルを回す)

### 役割

モデルの出力を受け取った後に、決定論的なテストや独立した評価器 (Evaluator) で正否を判定し、失敗していればエラーログや差分をコンテキストに添えて再試行させるフィードバック制御を担う。

### ここで直すべき失敗

- 1 回の推論 (ゼロショット) では完結しないケアレスミスや細部のバグ。
- コンパイルエラー、型エラー、テスト失敗が発生したまま止まってしまい、自律修復が行われない問題。

### 対策

1 発の推論で完璧な正解を出させようとしてプロンプトを複雑怪奇にするのではなく、「出力 → 検証 → エラーフィードバック → 修正」という REPL 的なループを組む。
特に、コードを書いた Builder 自身に「自分のコードは正しいか」を自己採点させるのではなく、決定論的なテストスクリプトや独立した `EVALUATOR.md` の基準で合否を判定させることが重要になる。

## 3. グラフ層 (Graph Engineering — 役割分担と状態遷移を設計する)

### 役割

単一のループでは扱いきれない複合的なタスクにおいて、複数のエージェントや作業フェーズを配置し、「どの条件を満たしたら・どのタスクを・どのノードに渡すか」という状態遷移 (DAG やステートマシン) を制御する最上位の層である。

### ここで直すべき失敗

- タスクの実行順序の崩壊 (例: 必要なデータや仕様が揃う前に実装や要約を始めてしまう)。
- マルチエージェント間でのコンテキスト迷子、伝達漏れ、またはフェーズ間の無限往復ループ。
- 作業プロセス自体の粒度や分割軸の設計ミス。

### 対策

この層で起きている問題に対し、個別ノードのプロンプトを書き換えたり単一ループのリトライ回数を増やしたりしても解決しない。
状態遷移グラフのルーティング条件を見直し、フェーズ間のゲート制御 (たとえば Planner と Builder が `CONTRACT.md` で合格基準に合意してから実装に入り、完了時は `HANDOFF.md` で状態を渡して Evaluator の検査を通すフロー) を根本から再設計する。
