# Thoughtworks Technology Radar Vol.33: Techniques

Thoughtworks Technology Radar Vol.33 (2025 年 11 月) の Techniques (手法) 象限の要約である。
AI コーディングでの知識の渡し方、エージェントと MCP のセキュリティ、GPU を扱うスケジューリング、AI に関するアンチパターンが多い。
リングの意味と今号のテーマは [全体像の文書](/references/ai/thoughtworks-technology-radar-vol-33/thoughtworks-radar-vol-33-overview.md) を参照する。

- 出典: Thoughtworks Technology Radar Volume 33 (PDF)、[thoughtworks.com/radar](https://www.thoughtworks.com/radar)

[TOC]

## Adopt

### 1. Continuous compliance

- 規制やセキュリティの基準を満たしているかを、自動化によって継続的に確かめる手法である。手作業の確認は遅く誤りやすいが、自動の確認は速く、証拠も残る。
- Open Policy Agent などの policy-as-code や SBOM の生成を、SLSA に沿って CD パイプラインに組み込む。OSCAL も大規模な自動化の枠組みとして有望である。
- 手法も道具も成熟したため Adopt に移った。AI が生成したコードへの慢心のリスクがある今、開発工程にコンプライアンスを組み込む重要性が増している。

### 2. Curated shared instructions for software teams

- 個人のプロンプトから一歩進め、効果の確かめられた AI への指示をチームで共有する。コーディングだけでなく、デリバリーの全作業に使う。
- 最も簡単なのは AGENTS.md などの指示ファイルをリポジトリにコミットすることである。Cursor、Windsurf、Claude Code はカスタムのスラッシュコマンドやワークフローで指示を共有できる。
- コーディング以外の作業には組織全体のプロンプト集を用意する。誰かが指示を改善すれば、すぐにチーム全体が恩恵を受ける。

### 3. Pre-commit hooks

- Git のフックは昔からあるが、まだ十分に使われていない。AI やエージェントによるコーディングで、シークレットや問題のあるコードを誤ってコミットするリスクが増えた。
- CI など検証の仕組みは他にもあるが、pre-commit フックは単純で効果的な安全策である。
- 遅いチェックを詰め込むと使われなくなるので、シークレットの検出のように、この段階で捕まえるのが最も効果的なものに絞る。

### 4. Using GenAI to understand legacy codebases

- GenAI を使うと、大きく複雑なレガシーシステムの理解が大幅に速くなる。Cursor、Claude Code、Copilot、Aider、Swimm などで、業務ルールの抽出、ロジックの要約、依存関係の特定ができる。
- 複数の顧客での経験から、実験ではなく実用的な既定の手段になった。GraphRAG のような高度な方法は準備の手間がコードベースの規模に応じて増えるが、生産性への効果は一貫して大きい。

## Trial

### 5. AGENTS.md

- AI コーディングエージェントに、プロジェクトでの作業の指示を渡す共通の形式である。エージェント向けの README にあたり、Markdown であること以外に必須の項目は無い。
- 典型的な内容は、開発環境の道具の使い方、テストの手順、コミットの作法である。出発点となるファイルの単純な約束事を作ったことに価値がある。

### 6. AI for code migrations

- 言語の書き換えや依存・フレームワークの更新などのコード移行は、手作業で何か月もかかることが多い。
- AI だけに任せると費用がかさみ、会話が迷走しやすい。あるチームは .NET の更新で、従来の更新パイプラインとコーディングエージェントを組み合わせ、コンパイルエラーの分析、移行の差分の生成、テストでの確認という小さく確かめられる段階に分けた。
- 時間の短縮効果は一様ではないが、開発者の単純作業を減らせる可能性ははっきりしている。

### 7. Delta Lake liquid clustering

- Delta Lake のテーブルで、パーティションと Z-order の代わりに使うクラスタリングの手法である。従来は作成時にキーを決め、変えるには全データの書き直しが必要だった。
- liquid clustering は木構造のアルゴリズムでキーごとにデータをまとめ、キーを全データの書き直しなしに少しずつ変えられる。Databricks Runtime では過去のクエリから最適な列を選んで自動で行う。

### 8. Self-serve UI prototyping with GenAI

- Claude Code、Figma Make、Miro AI、v0 などで、プロダクトマネージャーが文章のプロンプトから操作できるプロトタイプを直接作る手法である。数分で動く HTML、CSS、JS ができる。
- 使い捨てで、磨き込みより学びの速さを優先する。見た目の完成度が高いと細部にこだわりすぎたり、本番の手間を過小評価されたりするので、期待値の管理が欠かせない。
- 利用者調査と併用し、調査そのものの代わりにはしない。

### 9. Structured output from LLMs

- LLM の出力を JSON や特定のクラスなど、決められた形式に縛る手法である。予測しにくい文章を、機械が読める決定的なデータ契約に変える。
- プロンプトでの指定、モデルが備える構造化出力、Outlines や Instructor による制約付きデコーディング (有限状態機械で妥当な出力を保証する) まで方法がある。
- 本番での成功例があり、Assess から Trial に移った。

### 10. TCR (Test && Commit || Revert)

- テスト駆動開発から派生したワークフローで、変更のたびにテストが通ればコミットし、失敗すれば変更を元に戻す。ごく小さな段階で進めることを促す。
- 仕組みはこのサイクルを自動化するスクリプトを用意するだけである。YAGNI や KISS などの良い習慣を強める。GenAI を使った新しい作り方を試す中で評価する価値がある。

## Assess

### 11. AI-powered UI testing

- 前号では探索的テストが中心で、LLM の非決定性による不安定さを指摘していた。
- MCP の登場で、Playwright や Selenium が自前の MCP サーバー (playwright-mcp、mcp-selenium) を出した。コーディングアシスタントが、各フレームワークの仕組みで安定した UI テストを生成できる。変化の速い分野で、Playwright Agents なども登場している。

### 12. Anchoring coding agents to a reference application

- かつての tailored service templates (新しいサービスの雛形) は、時間とともに既存サービスとの差が広がる。
- コーディングエージェントに、静的なプロンプトの例ではなく、コンパイルできる生きた参照アプリケーションを手本として与える。MCP サーバーが参照コードとコミットの差分を公開し、エージェントがずれを見つけて修正を提案する。

### 13. Context engineering

- 推論時に LLM へ渡す情報全体を、望む出力が確実に得られるように設計・最適化することである。プロンプトの言い回しだけを扱うプロンプトエンジニアリングより広い。
- 手法は 3 つに分けられる。
  - コンテキストの準備: 最小限のシステムプロンプト、代表的な少数の例、トークン効率の良いツール。
  - 長いタスクでのコンテキスト管理: 要約、外部メモリへの構造化されたメモ、サブタスクを分けて要約させるサブエージェント。
  - 動的な情報の取得: 必要になった時点でだけ外部データを読み込む just-in-time の取得。

### 14. GenAI for forward engineering

- レガシーシステムの刷新で、AI に既存コードが「何をするか」(仕様) を書かせ、「どう実装されているか」はあえて隠してから書き直す手法である。仕様駆動開発をレガシーの刷新に当てはめたものにあたる。
- 逆方向の解析 → 設計 → 順方向の実装というループで、人もエージェントも高い抽象度で考えられる。隠れたロジックや例外を見つけ、現在の構造に縛られない解決策を探れる。

### 15. GraphQL as data access pattern for LLMs

- LLM がデータを取得するための、統一されたモデル向けのアクセス層として GraphQL を使う。モデルにデータベースへの直接アクセスを与えずに済む。
- REST のように取りすぎることがなく、必要なデータだけを取れるので、雑音とトークンが減る。スキーマが実体と関係のメタデータになり、エージェントがそれをもとに問い合わせを組み立てられる。
- 良いスキーマと意味のあるフィールド名が前提である。DoS 攻撃の入口の増加や、キャッシュとバージョン管理という GraphQL の通常の課題にも注意する。

### 16. Knowledge flows over knowledge stocks

- 組織の知識をシステムとして捉え、蓄積された知識 (ストック) と、知識が組織の中を動き変化する流れ (フロー) に分けて考える。
- 外部の知識の流入を増やすほど革新が起きやすい。実践コミュニティを作ることや、多様な外部の情報源を意図して求めることが流れを増やす。
- GenAI で既存の知識のストックに手が届きやすくなった今こそ、新しい考えと外部の視点を育てることが同じくらい重要である。

### 17. LLM as a judge

- 別の LLM の出力を LLM に評価させる手法である。新たに分かった複雑さとリスクを反映し、Trial から Assess に下げた。
- 位置のバイアス、冗長さへのバイアス、頑健性の低さがあり、人の判断の代わりとしては当てにならないことが多い。学習パイプラインに使うと、自分の系統の出力を好むバイアスや、学習と評価の境界の曖昧化を招き、性能の数字が実態以上に膨らむ。
- 複数のモデルで合議させる (LLMs as a jury) などの改善策は、信頼性を上げる一方で費用と複雑さも増す。重要な工程に組み込む前に、人による確認と透明性を確保する。

### 18. On-device information retrieval

- 検索や RAG を、利用者の端末 (モバイル、デスクトップ、エッジ) の中だけで動かす手法である。軽いローカルのデータベースと、端末上の推論に最適化したモデルを組み合わせる。
- 例として、SQLite でベクトル検索ができる sqlite-vec と、3 億パラメーターの埋め込みモデル EmbeddingGemma の組み合わせがある。データ主権、低遅延、プライバシーが重要なローカルファーストの用途で評価する。

### 19. SAIF

- Google の Secure AI Framework で、AI のセキュリティリスクを管理するための実用的な手引きである。データ汚染やプロンプトインジェクションなどの脅威を、リスクの地図、構成要素の分析、対策で整理する。
- エージェントのシステムを作るときのリスクに焦点を当てている点が時宜にかなっている。

### 20. Service mesh without sidecar

- サイドカー型のサービスメッシュの費用と運用の複雑さに対し、Istio の ambient mode という選択肢が出てきた。
- ノードごとの L4 プロキシ (ztunnel) と、名前空間ごとの任意の L7 プロキシ (Waypoint proxy) に役割を分ける。小規模なクラスターでは良い経験を得ており、大規模な事例を待っている。

### 21. Small language models

- 小さな言語モデル (SLM) でもエージェントの AI を効率よく動かせる証拠が増えている。今のエージェントのワークフローの多くは、高度な推論の要らない狭い反復作業だからである。
- Phi-3、SmolLM2、DeepSeek などの進歩で、こうした作業には十分な能力がある。費用、遅延、資源消費も少ない。エージェントのワークフローでは SLM を既定にし、必要なときだけ大きな LLM を使うことを検討する価値がある。

### 22. Spec-driven development

- 構造化された機能仕様から始め、小さな部分、解決策、タスクへと段階的に分解する AI コーディングのワークフローである。用語の定義はまだ固まっていない。
- 3 つの道具が異なる解釈を示している: Amazon の Kiro (要件、設計、タスクの 3 段階)、GitHub の spec-kit (同様の 3 段階に、決して破ってはならない原則を書く constitution を追加)、Tessl Framework (コードではなく仕様そのものを保守する成果物にする)。
- ワークフローは凝っていて独自色が強い。長くてレビューしにくい仕様を生成することもある。AI のために細かいルールを手で作り込むことはいずれ拡張しないという「苦い教訓」を学び直しているのかもしれない。

### 23. Team of coding agents

- 1 人の開発者が、アーキテクト、バックエンド担当、テスト担当など役割の違う複数の AI コーディングエージェントを指揮して、1 つの開発タスクに協力させる手法である。Claude Code、Roo Code、Kilo Code のサブエージェントや複数のモードで支えられる。
- LLM に役割を与えると出力の質が上がるという原則に基づく。最適な分け方はまだ探っている段階である。

### 24. Topology-aware scheduling

- GPU は単体ではなく、密に結合したアクセラレーターの網になり、性能は配置とトポロジーに左右される。NVL72 のように 72 個の GPU が 1 つのアクセラレーターとして動く構成でも、スイッチの境界をまたぐと集団通信がボトルネックになる。
- NVLink、PCIe、NIC のトポロジーを無視するスケジューラーは、複数 GPU のジョブをばらばらに置いて効率を落とす。
- 学習は帯域に縛られるので、連続した NVLink の島にまとめて置く。推論は遅延と SLO に縛られるので、可用性のための複製と、MoE や KV キャッシュの局所性を保つ分割のバランスを取る。Kueue などを評価している。

### 25. Toxic flow analysis for AI

- エージェントが、非公開データへのアクセス、信頼できない内容への接触、外部との通信の 3 つ (lethal trifecta) を併せ持つと、非常に脆弱になる。LLM は入力中の指示に従いやすく、データを外に送れという指示を含む内容で情報が漏れる。
- エージェントのシステムのデータの流れのグラフを調べ、危険な経路を特定する手法である。まだ初期段階だが、エージェントと MCP サーバーに対する新しい攻撃を見つける有望な方法の 1 つである。

## Hold

### 26. AI-accelerated shadow IT

- AI により、コードを書かない人が IT 部門を待たずにソフトウェアを作り、つなげられるようになった。ノーコードの自動化基盤が AI の API と連携し、チャットのメッセージを ERP の API 呼び出しに変えるような「つぎはぎ」が容易になった。
- これは今も重要な業務を支えるスプレッドシートの次の進化に見えるが、規模はずっと大きい。放置すると、統制されず安全でないアプリが増え、データが多くのシステムに散らばる。

### 27. Capacity-driven development

- 1 つの価値の流れ (利用者の体験やプロダクト) に集中すべきストリームアラインドチームが、手が空いたときに他のプロダクトの機能を引き受ける傾向である。
- 短期的には効率的に見えるが、局所最適にすぎない。常態化すると認知負荷と技術的負債が増え、文脈の切り替えの費用が積み重なって詰まる。
- 手が空いたらシステムの健全性の改善に充てる。WIP 制限、クロストレーニング、動的なチームの組み替えで容量を管理する。

### 28. Complacency with AI-generated code

- AI コーディングアシスタントやエージェントの普及とともに、AI が生成したコードへの慢心を示すデータや研究が増えている。GitClear の 2024 年の調査では、重複コードとコードの書き換えが増え、リファクタリングが減った。
- Microsoft の研究は、AI による自信が批判的思考を犠牲にしがちだと示している。エージェントはより大きな変更を生成するので、レビューが難しくなりリスクが増す。
- TDD や静的解析などの確立した実践を強化し、チームで共有する指示などでコーディングのワークフローに組み込むことを勧めている。

### 29. Naive API-to-MCP conversion

- 社内の API をそのまま MCP に変換して、AI エージェントに既存システムを使わせようとすることである。MCP link や FastAPI-MCP などの道具がこれを支援している。
- 人の開発者向けに作られた細かい API を AI がつなぎ合わせると、トークンの浪費、コンテキストの汚染、エージェントの性能低下を招く。機密データの公開や破壊的な操作も、エージェントに対しては確実に防ぐ方法が無い。
- 既存の API の上に、エージェントのワークフロー専用の安全な MCP サーバーを設計することを勧めている。

### 30. Standalone data engineering teams

- データパイプラインやデータ製品を、利用する業務ドメインから切り離した独立のデータエンジニアリングチームが作り所有する形は、アンチパターンである。DevOps やテストを分離した過去の失敗の繰り返しで、知識のサイロとボトルネックを生む。
- データ基盤チームは共有の基盤の保守に集中し、業務の横断チームが自分たちのデータ製品を作り所有する (データメッシュの原則)。

### 31. Text to SQL

- LLM で自然言語を実行可能な SQL に変えるが、信頼性が期待に届かないことが多い。出力が見えない、または自動で実行される無監督のワークフローでの利用を避けるよう Hold に移した。
- スキーマやドメインの理解が限られるために幻覚が起き、誤ったデータの取得や意図しない変更につながる。生成されたクエリはすべて人がレビューする。
- エージェントによる BI では、データベースに直接触れさせず、Cube や dbt のセマンティックレイヤー、あるいは GraphQL や MCP のような意味の豊かなアクセス層を使う。
