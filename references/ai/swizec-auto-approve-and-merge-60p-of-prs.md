# PR の 60% を自動承認・自動マージするにはどうすればよいか

Swizec Teller のブログ記事 [How do we auto-approve and merge 60% of PRs?](https://swizec.com/blog/how-do-we-auto-approve-and-merge-60p-of-prs) (2026-11-07 公開) の要約。
AI コーディングエージェントの普及によってプルリクエスト (PR) が急増するなか、現状 15〜16% にとどまっている自動承認率を 60% まで引き上げるためのリスク分類手法と、人間のレビュー負荷を実装の前後へ移すプロセス改革を解説している。

## 背景と課題: コードレビュー疲れと 15〜16% の壁

- AI エージェントによるコード生成が日常化した結果、作成される PR の数が急増し、人間のエンジニアが「コードレビューに溺れる」状態が起きている。
- 本番環境を壊しかねない高リスクな変更、複数サービスにまたがる協調デプロイ、ジュニアエンジニアの育成といった目的があるため、PR の 100% を自動マージすることは現実的ではない。
- しかし、日常のコード変更の大半はそこまで重大なリスクを持たないため、現状の 15〜16% という自動承認率を 60% まで引き上げることを現実的な目標として掲げている。

## 保守的すぎるガードレールの限界

初期の自動承認ボットは、安全性を優先するあまり、以下のような領域に触れる PR をファイルパスやモジュール単位で一律にブロックしがちである。

- 決済・金融モジュール (Financial / billing modules)
- データベースのマイグレーション (Database migrations)
- 公開 API やリポジトリ間のインターフェース (Public APIs / interfaces)

このような粗いルールでは、金融モジュール内の単なる文言修正や、既存データを壊さない安全なカラム追加までもが「高リスク」と判定されて人間のレビュー待ちになり、自動化の割合を増やす上での最大のボトルネックになる。

## 「一律ブロック」から「スマートなリスク分類」への進化

自動承認率を 60% に近づけるには、触れたディレクトリではなく「変更の実質的なリスク」を判定するスマートな分類器が必要になる。

### マイグレーションの精査

- データベースに関わる変更をすべて止めるのではなく、LLM 等の分類器を使ってマイグレーションの中身を解析する。
- カラム削除や型変更などの「破壊的なスキーマ変更」と、NULL 許容カラムの追加などの「安全な追加」を見分け、後者は自動承認の対象に含める。

### 宣言された API コントラクトの検証

- リポジトリをまたぐ変更や API 層へのタッチを一律に拒否するのではなく、宣言された API コントラクトに照らして検証する。
- その変更が既存の呼び出し元を壊す破壊的変更 (Breaking Change) かどうかを自動検出し、後方互換性が保たれていれば通過させる。

### UI とコアロジックの分離

- 同じ重要モジュール内であっても、UI コンポーネントや表示の微調整と、コアビジネスロジックの変更とでリスクプロファイルを分離して判定する。

## レビュー負荷を「実装中」から「実装前」と「実装後」へ移す

PR の自動マージを増やすことは、品質確認を放棄することではなく、人間が関与するタイミングを「コードが書かれた直後 (PR レビュー)」から「実装前」と「実装後」へシフトさせることを意味する。

| フェーズ | 主な担当 | 実施する内容 |
| :--- | :--- | :--- |
| 実装前 (Before implementation) | 人間 (エンジニア・ステークホルダー) | アーキテクチャ、制約条件、プロダクトの方向性について事前に合意形成する。 |
| 実装中 (During implementation) | エージェント・リンター・自動テスト | 正確性、コードスタイル、安全性の検証を機械と決定論的ルールで自動化する。 |
| 実装後 (After implementation) | 人間 (チーム全体) | 動くソフトウェアを実際に触る UX ローストセッション等でプロダクト品質を確かめる。 |

### 1. 実装前 (Before implementation)

- コードを書き始める前に、アーキテクチャ上の制約やプロダクトの方向性について、エンジニアとステークホルダーの間で合意を形成しておく。
- 方向性のズレを PR が作られた後に指摘するのではなく、入り口の段階で揃える。

### 2. 実装中 (During implementation)

- コードの正確性、スタイルの一貫性、安全性のチェックは、人間の目視ではなく機械に任せる。
- 具体的には、AI レビューエージェント、人間が過去に繰り返した細かい指摘 (nitpick) をルール化した決定論的なカスタムリンター、そして E2E テストを組み合わせて自動で保証する。

### 3. 実装後 (After implementation)

- 人間の貴重なエネルギーは、PR 上でコードの行単位の粗探しをすることには使わない。
- 代わりに、デプロイされた実際のソフトウェアをチームで触って使用感を厳しく確かめる「UX ロースト (UX roasting) セッション」や、プロダクトの目標が本当に達成されているかの確認に集中させる。
