# Scott Hurff: The UI Stack 要約

プロダクトデザイナーの Scott Hurff による記事「Why your user interface is awkward: You're ignoring the UI stack」の要約である。
著者の書籍 _Designing Products People Love_（O'Reilly、2016 年 1 月）からの抜粋として掲載されている。
外部資料の要約であり、最終的な根拠は原典を参照すること。
要点は「どの画面にも最大 5 つの状態（Ideal、Empty、Error、Partial、Loading）があり、それらと状態間の遷移をすべて設計しないと Awkward UI になる」である。

## Awkward UI とは

出典: (冒頭)

Awkward UI とは、生気のない、何かが欠けているように感じる UI のことである。
例として、読み込み表示がない、どこで何が失敗したかを伝えない（怖いエラーメッセージを出す場合もある）、データが少ないと見え方がおかしいグラフ、新しいデータが線形に突然所定の位置へ入ることが挙げられている。
著者の実例として、Apple TV の購入済み映画の画面は、読み込み表示がなく、映画が突然現れるため、毎回不安になるとしている。
映画の再生を始めるときは、準備中の表示があるので体験が違う。

コンピュータは怠惰であり、何が新しいか、次に何をすべきか、問題が起きたときにどう反応すべきかを人に伝えようとしない。
人はフローで考え、物理世界の動き（ドアは弧を描いて開く、物は動くのが見える）に慣れている。
プロダクトデザイナーがこれを考慮しないと、UI Stack の規則を破ることになり、Awkward UI が生まれる。

## UI Stack と 5 つの状態

出典: The UI Stack

どの画面も複数の顔を持ち、文脈に応じて現れる。
デザインの用語ではこれを状態（state）と呼び、作るすべての画面で考えるべきだとしている。
サーバーの応答には時間がかかり、顧客は想定どおりに使うとは限らないため、1 つの状態だけの画面はほぼない。
UI Stack の規則と 5 つの状態に従うと、寛容で、役に立ち、人間的な、まとまりのある UI になる。

1 つの画面は、最大で次の 5 つの状態を持つ。

1. Ideal State（理想の状態）
1. Empty State（空の状態）
1. Error State（エラーの状態）
1. Partial State（一部だけある状態）
1. Loading State（読み込み中の状態）

顧客はフローを進むにつれ、これらの状態の間をなめらかに行き来する。
着想は、2004 年に Basecamp（当時の 37signals）が書いた「The Three State Solution」（regular、blank、error の 3 状態）である。
著者はこれに、AJAX の普及、モバイルアプリ、技術の大衆化という変化を踏まえた 5 状態として手を加えたとしている。

## Ideal State

出典: Ideal State

プロダクトが最大の価値を出し、役立つ中身であふれている状態である。
最初に作る状態であり、顧客に最もよく見せたいものである。
マーケティングページやアプリストアのスクリーンショットのようなものと考える。

この状態が、ほかのすべての状態の土台と調子を決める。
中核の UI は反復で大きく変わり得るので、その影響はほかの状態に及ぶ。
すべての状態は Ideal State に通じるので、まずこれを作り、顧客の問題の解決に近づくにつれてほかの状態を整える。
例として、Tinder は市場で最良の Ideal State の 1 つを持つとしている。

## Empty State

出典: Empty State

Empty State は 1 画面より大きな話であり、顧客に良い第一印象を与え、行動を促し、関心を保ち、価値を思い出させるためのものである。
後付けにすると、圧倒的な体験か、冷たく味気ない体験になりやすい。
大きく 3 種類ある。

1. 顧客が初めて使うとき（First-time use / Onboarding）
1. 顧客が自分でデータを消したとき（User-cleared data）
1. 表示するものがないとき（No results）

### First-time use / Onboarding

データがあるときに何が見えるかを説明できる、一度きりの機会である。
著者は、これを Joseph Campbell の「ヒーローの旅」になぞらえ、顧客を冒険に呼び、力を得た存在に変えるものと説明している。
コーチマーク（説明用のオーバーレイ）は考え不足の初回体験の典型であり、学ぶ負担を顧客に負わせ、操作を中断させるとしている。
アイデアとして次が挙がっている。

- 前向きな文面で、何をすればよいかを平易に書く。
  「Nothing to see here」は何も伝えない。
  押すべきボタンと、その理由を伝えるほうがよい。
- プロダクトの中身で操作を教える。
  例として、メッセージアプリなら、初回の受信箱に「tap to open me」という件名のメッセージを入れる。
- Ideal State のときの画面のスクリーンショットを例として見せる。
- 顧客の進み具合を見て対応する。
  同じ画面に長く留まるなら、ライブチャットで声をかけられる。

良い例として、Hipchat（やることを直接伝える）、Facebook Paper（操作を少しずつ教える）、Basecamp（代わりの内容を置く）、Airbnb の Wish List（簡潔で明確な行動の呼びかけ）が挙げられている。
オンボーディングの詳細は Samuel Hulick の _The Elements of User Onboarding_ を勧めている。

### User-cleared data

顧客が自分でデータを片付けた場合（to-do を終えた、通知を読んだ、メールをアーカイブした、音楽をダウンロードし終えた、など）である。
顧客に報いるか、次の行動を促す機会である。
データを片付けた顧客はプロダクトに関与している顧客なので、次の一歩を顧客に考えさせず、プロダクトが先回りしてフローに留める。
例は、Inbox Zero で写真を見せる、ダウンロードが終わったら聴くよう促す、通知を読み終えたら別の読み物を示す、である。

### No results

検索や閲覧で見つからなかった場合は、顧客の意図を推測して賢い提案をする機会である。
Amazon は綴りの誤りや似た検索を考慮し、最も近い結果を示して、一致しなかった語も見せるので、結果が空になることがまれである。
Pinterest は、検索語がどう解釈されたかが分かるので、顧客が検索語を直しやすい。
教訓は、顧客を行き止まりに追い込まず、使えるものか別の道を示すことである。

## Error State

出典: Error State

物事がうまくいかなかったときの画面である。
1 画面にとどまらないことが多く、エラーは意外な組み合わせで起きる。
フォームの未入力や不正、サーバーに接続できない、アップロードが終わる前に次へ進もうとする、テキストを送信せずにページを離れる、などが含まれる。

- エラーのときも、ユーザーの入力をすべて守る。
  Jef Raskin の言葉として「コンピュータはあなたの作業を損なってはならず、何もしないことで損なわれるに任せてもならない」という趣旨が引用されている。
  例として、航空会社のサイトが、セキュリティコードの入力漏れでページを再読み込みし、入力済みの情報を消すことが挙げられている。
- 理想は、データを消さずに動的にエラーを検出することである。
  再読み込みが必要なら、不完全でも入力を保存する。
  再読み込みでエラーを検出するのは、多くの場合、怠慢の表れだとしている。
- 大げさで曖昧なエラーにしない。
  Blue Screen of Death、Kernel Panic、「Abort, Retry, Fail?」は、衝撃と恐れと混乱で記憶されているとする。
- 文面は簡潔で、親しみやすく、次に何をすべきかを示す。
  曖昧なエラーコードや 16 進数、分かりにくい選択肢は、人を怖がらせ苛立たせる。
  顧客が技術者なら技術的なメッセージが合う場合もあるが、一般にはそぐわなくなってきている。
- エラーメッセージは人間向けで、顧客に合ったものにする。
  「何かがうまくいかなかったとき、自分なら何を伝えてほしいか」を考える。

## Partial State

出典: Partial State

空ではなくなったが、まだ少ししかデータがない画面である（1 行だけ、写真が数枚、プロフィールが途中、など）。
ここでの仕事は、顧客が落胆して使うのをやめるのを防ぐことである。
マイクロインタラクションを設計し、Ideal State の全体像へ導く機会である。

ゲームデザインの「acceleration（加速）」の考え方が役立つとしている。
これは、将来もっと強くなる自分をプレイヤーに思い描かせ、決まった一連の作業へ導くものである。
Clash of Clans のように顧客に結晶を集めさせることではない。
例として、LinkedIn の「Profile Completeness」バー（100% までに必要な作業を示す）と、Dropbox の追加ストレージまでの残り手順の表示が挙げられている。
Dropbox の手順は、顧客に教え、活用させる効果も持つ。

## Loading State

出典: Loading State

後付けにされやすいが、期待を設定する責任が伴う状態である。
データ取得、接続待ち、画面遷移のときの表現が対象で、画面全体を覆う、領域ごとに遅延読み込みする、フォーム項目でユーザー名の空きを調べるときのようにインラインで出す、といった形がある。
体感も実際の速度と同じくらい重要である。
空白とスピナーで画面を埋めると、顧客が時計を見ることになり、進捗そのものより進捗の表示に注意が向く。

Luke Wroblewski の Polar では、投票ごとにスピナーを入れたところ、顧客は「以前より遅い」と感じて不満を述べた。
同氏は「進捗の表示を見せたことで、人に時計を見させてしまった」と述べている。

### Skeleton Screens

Wroblewski が名付けた手法で、読み込み中であることではなく、読み込まれる中身に注意を向けさせる。
ページの基本構造を先に表示し、ダウンロードされるにつれて欠けた部分を埋める。
スピナーをなくせる場合があり、体感の性能を高められる。
Pinterest は画像の平均色で背景を塗り、読み込み前から完成形を想像させる。
Facebook は、中身に似た形を「shimmer effect」で脈動させ、読み込み中を伝える。

### Optimistic actions

Instagram の共同創業者 Mike Krieger の言葉「誰も待っている間に待ちたくはない」が引かれている。
操作が成功すると仮定して先に完了として扱い、サーバーへの要求は裏で行うと、速く見える。
例は「いいね」とコメントである。
写真の投稿も、「Done」を押すときではなく、フィルターを選んだ直後にアップロードを始める。
最適な実装ではなく、戻るとデータが捨てられるかもしれないが、「誰も見ていないときにビットを動かす」ことで速く見せられる。

## 状態の遷移（メッセージアプリの例）

出典: (UI Stack の例)

状態は単独で存在せず、プロダクトがいつでも呼び出せる縦の軸に並ぶ。
各状態を考慮するだけでなく、画面が状態間をどう移るかも設計する。
著者はメッセージアプリを例にし、次の対応を挙げている。

- メッセージがない: Empty State
- 一方だけが送った: Partial State
- 相手の入力中表示、送信中、配信確認: Loading State
- 送信に失敗: Error State（再送の操作も、読み込み表示の一種を伴う）
- 会話が成り立った: Ideal State

例として、空の画面を押し流して 1 通目の送信で Partial State に移し、入力中の表示から新しいメッセージへと既存のメッセージを押しのけて入れ替える。
文字が入ると「Send」ボタンが灰色（無効）から青（有効）に変わる。
送信中はメッセージを薄く表示し、「delivered」の表示で成功を伝える。
失敗すると赤い印が出て薄い「undelivered」の状態になり、タップで再送する。

遷移の要素がないと、状態が突然現れたり消えたりして、顧客を混乱させる。
これらの実装にはデザインと開発の密な協力が必要で、すべての状態に時間をかけるべきだとしている。

## まとめ（記事末尾の要約）

出典: A plot summary of the stunning tale you just read

- Ideal State だけを設計し、ほかの状態を後付けにしない。
  各状態が、顧客を目的の達成まで導くようにする。
- Loading State をプロトタイピングの対象に含める。
  開発と協力し、体感の、可能なら実際の性能も高める。
- エラーを起こすエッジケースを考え、最も痛いものはカバーし、顧客のデータを守る。
  費用と効果のトレードオフはある。
