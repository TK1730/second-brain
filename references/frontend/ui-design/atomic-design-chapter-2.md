# Atomic Design: Chapter 2 Atomic Design Methodology 要約

Brad Frost の書籍『Atomic Design』（オンラインで無料公開されている）の第 2 章「Atomic Design Methodology」の要約である。
外部資料の要約であり、最終的な根拠は原典を参照すること。
要点は「UI を atoms、molecules、organisms、templates、pages の 5 段階で捉える」「これは直線的な工程ではなく、部分と全体を行き来するための考え方である」の 2 つである。

## 化学からの着想

出典: Taking cues from chemistry

- 著者は、複雑なものを作る方法を他の分野に求めた。
  工業デザインや建築では、飛行機、船、超高層ビルのような非常に複雑なものを作るために、賢いモジュール式の仕組みが作られてきた。
- 探求は自然界に戻り、高校の化学の授業の記憶につながった。
  化学反応は化学式で表され、原子の元素が結びついて分子になる様子を示すことが多い。
- 自然界では、原子の元素が結びついて分子になり、分子がさらに結びついて比較的複雑な有機体になる。
  - Atoms は、あらゆる物質の基本の構成要素である。
    各元素は固有の性質を持ち、意味を失わずにはこれ以上分けられない。
    原子はさらに小さな粒子からなるが、原子は機能する最小の単位である。
  - Molecules は、化学結合で結びついた 2 つ以上の原子の集まりである。
    固有の性質を持ち、原子よりも具体的で、機能的になる。
  - Organisms は、1 つのまとまりとして働く分子の集まりである。
    単細胞生物から人間のような高度な生物までを含む。
- この原子論により、既知の宇宙のあらゆる物質は、有限の原子の元素に分解できる。

## Atomic design の方法論

出典: The atomic design methodology

- インターフェースも、同様に有限の要素に分解できる。
  Josh Duck の Periodic Table of HTML Elements は、ウェブサイトやアプリがすべて同じ HTML 要素からできていることを示している。
- 有限の構成要素から始めるので、自然界と同じ過程を UI のデザインと開発に当てはめられる。
- Atomic design は、インターフェースのデザインシステムを、より意図的で階層的に作るための、5 つの段階からなる方法論である。
  1. Atoms
  1. Molecules
  1. Organisms
  1. Templates
  1. Pages
- Atomic design は直線的な工程ではなく、UI をまとまった全体としても、部品の集まりとしても同時に考えるための心の中のモデル（mental model）である。
  5 つの段階は、デザインシステムの階層の中でそれぞれ重要な役割を持つ。

## Atoms

出典: Atoms

- 物質の基本の構成要素が原子であるように、インターフェースの atoms は、すべての UI を構成する土台の部品である。
- 例は、フォームのラベル、入力欄、ボタンなどの基本の HTML 要素で、機能を保ったままではこれ以上分けられない。
- 自然界の原子は固有の性質を持ち、水素原子は電子を 1 つ、ヘリウム原子は 2 つ持つ。
  この性質が応用に大きく影響する例として、ヒンデンブルク号の事故は、不活性なヘリウムではなく可燃性の水素で満たされていたために大惨事になった、と述べられている。
- 同様に、インターフェースの atoms も、ヒーロー画像の寸法や主見出しのフォントサイズなどの固有の性質を持つ。
  これらの性質が、その atom を UI 全体にどう使うかに影響する。
- パターンライブラリでは、atoms はすべての基本のスタイルを一目で示し、デザインシステムの開発と保守で繰り返し参照できる。
  ただし、自然界の原子と同様に、単独では存在せず、使われて初めて生きてくる。

## Molecules

出典: Molecules

- 化学では、molecules は結びついた原子の集まりで、新しい固有の性質を持つ。
  水と過酸化水素は、同じ元素（水素と酸素）からできていても、性質も振る舞いも大きく異なる。
- インターフェースの molecules は、1 つのまとまりとして働く、比較的単純な UI 要素の集まりである。
  例は、ラベル、検索の入力欄、ボタンを組み合わせた検索フォームである。
- 組み合わせることで、抽象的だった atoms に目的が生まれる。
  ラベルが入力欄を定義し、ボタンを押すとフォームが送信される。
  結果は、検索機能が必要などこにでも置ける、単純で持ち運べて再利用できる部品になる。
- 要素を単純なまとまりに組むことは昔からしてきたが、それに 1 つの段階を割くと、いくつかの気づきが得られる。
- 単純な部品を作ると、単一責任の原則（do one thing and do it well）に従いやすい。
  1 つのパターンに複雑さを背負わせすぎると、ソフトウェアは扱いにくくなる。
  そのため、単純な molecules を作ると、テストがしやすくなり、再利用が促され、インターフェース全体の一貫性が高まる。

## Organisms

出典: Organisms

- Organisms は、molecules や atoms、ほかの organisms の集まりからなる、比較的複雑な UI 部品である。
  インターフェースの独立した区画を形成する。
- 検索フォームの molecule を、ヘッダーの organism に置く例が示されている。
  ヘッダーは、ロゴ、主要なナビゲーション、検索フォームのような、性質の異なる要素からなることがある。
  ヘッダーは、より小さな部品を含んでいても、インターフェースの独立した区画である。
- 同じ molecule を繰り返し並べた organism もある。
  例は、e-コマースのカテゴリのページの、商品を格子状に並べた一覧である。
- Atoms から molecules、より複雑な organisms へと組み上げると、設計者と開発者に文脈の感覚が生まれる。
  Organisms は、小さく単純な部品が実際に働く様子を示し、何度も使える独立したパターンになる。
  商品の一覧の organism は、カテゴリの一覧、検索結果、関連商品など、商品の集まりを表示するどこでも使える。

## Templates

出典: Templates

- ここで化学の比喩に別れを告げる。
  atoms、molecules、organisms の言葉は、部品を意図的に組み立てるための階層を与えるが、最終的な成果物については、顧客や上司、同僚に通じる言葉に移る必要がある。
  比喩を引っ張りすぎると、関係者を混乱させるおそれがある。
- Templates は、部品をレイアウトに置き、デザインの土台にある内容の構造を示す、ページ単位のものである。
  例は、ヘッダーの organism をホームページの template に当てはめたものである。
- 部品がレイアウトの中でどう見え、どう働くかを示し、部分が全体としてうまく働くことを示すことが、デザインシステムでは重要である。
- Templates は、ページの最終的な内容ではなく、土台にある内容の構造に注目する。
  デザインシステムは内容が動的に変わることを考慮する必要があるので、画像の大きさや、見出しや文章の文字数などの部品の性質を明示するとよい。
- Mark Boulton の言葉が引かれている。
  内容を知らなくても良い体験は作れるが、内容の構造（what your content is ではなく what your content is made from）を知らずには良い体験を作れない。
- ページの骨格を定めると、さまざまな動的な内容に対応しつつ、特定のパターンに入る内容の種類に必要な歯止めも与えられる。

## Pages

出典: Pages

- Pages は、templates の具体的な実例で、実際に代表的な内容を入れたときの UI を示す。
  Template に代表的な文章、画像、メディアを流し込む。
- Pages は、atomic design で最も具体的な段階である。
  利用者が実際に目にして操作するもので、関係者が承認するものでもある。
- Pages は、土台のデザインシステムが効果的かを試すためにも欠かせない。
  実際の内容を当てはめて、パターンがうまく機能するかを確かめ、問題があれば molecules、organisms、templates に戻って直す。
- 再利用できるデザインパターンを作るだけでなく、そこに入れる内容の現実も正確に反映したシステムを作る必要がある。
- Pages は、templates のバリエーションを明らかにする場でもあり、頑健なデザインシステムを作るうえで重要である。例は次のとおり。
  - 買い物かごの商品が 1 つの利用者と 10 個の利用者がいる。
  - ダッシュボードは最近の活動を表示するが、初めての利用者には隠す。
  - 記事の見出しが 40 文字のものも、340 文字のものもある。
  - 管理者の権限を持つ利用者には、追加のボタンや選択肢が見える。
- どの例でも、土台の template は同じで、内容の動的な性質に合わせて UI が変わる。
  このバリエーションは、土台の molecules、organisms、templates の作り方に直接影響する。
  バリエーションを考慮した pages を作ると、より回復力のあるデザインシステムになる。

## 5 段階のまとめ

出典: The atomic design methodology（Pages の末尾）

- Atoms: これ以上分けられない UI の要素で、インターフェースの基本の構成要素である。
- Molecules: atoms の集まりで、比較的単純な UI 部品を作る。
- Organisms: 比較的複雑な部品で、インターフェースの独立した区画を作る。
- Templates: 部品をレイアウトに置き、デザインの土台にある内容の構造を示す。
- Pages: templates に実際の内容を当てはめ、バリエーションを明らかにして、最終的な UI を示し、デザインシステムの回復力を試す。

## Atomic design の利点

出典: Advantages of atomic design

### 部分と全体

出典: The part and the whole

- 最大の利点の 1 つは、抽象と具体をすばやく行き来できることである。
  インターフェースを atoms まで分解して見ることも、それらがどう組み合わさって最終的な体験になるかを見ることも、同時にできる。
- Frank Chimero『The Shape of Design』の画家の比喩が引かれている。
  画家は、イーゼルから離れて全体を評価し、次の一筆を決め、近づいて描き、また下がって全体との関係で確かめる。
  これは「文脈を切り替える踊り」で、描くことと評価することの間に密なフィードバックの輪を生む。
- Atoms、molecules、organisms は単独では存在せず、templates と pages は小さな部品からできている。
  部品は全体に影響し、全体は部品に影響する。両者は絡み合っており、atomic design はこの事実を受け入れる。
- 1 つの部品を作るときは、キャンバスで細部を描く画家のようである。
  レイアウトの中で実際の内容と共に見るときは、少し下がって全体を評価する画家のようである。
  1 つの部品に集中して機能的で使いやすく美しいか確かめることも、最終的な UI の中でそうであるか確かめることも、どちらも必要である。
- 部品だけを単独で設計して、全体がまとまることを祈るのは愚かであるため、atomic design は直線的な工程ではないと繰り返されている。
  5 段階を「手順 1 は atoms、手順 2 は molecules ……」と解釈せず、最終的な UI とその土台のデザインシステムを同時に作るための mental model として捉える。

### 構造と内容の分離

出典: Clean separation between structure and content

- デザインと内容の議論は、鶏と卵に似ている。
  Mark Boulton によれば、「content then design」でも「content or design」でもなく、「content and design」である。
- 良くできたデザインシステムは、そこに入る内容に合わせてあり、良くできた内容は、UI での見せ方を意識している。
- Atomic design は、UI パターンの構造と、そこに入る内容の両方を語る言葉を与える。
  内容の構造の骨格（templates）と最終的な内容（pages）は明確に分かれるが、両者が互いに強く影響し合うことも認めている。
- 例として、人物のブロックの molecule を繰り返した骨格と、そこに代表的な内容を入れたものを比べている。
  人名がパターンの中で 5 行に折り返すなら、より atoms に近い段階で直す必要がある。
- Pages の段階で UI に流し込む内容は、土台のデザインパターンの性質や範囲に影響する。

### 名前について

出典: What's in a name?

- モジュール式の設計と開発は新しくないのに、なぜ modules、components、elements といった既存の語を使わないのか、という疑問に答えている。
- Components や modules といった語は、名前だけでは階層を読み取れない。
  Atoms、molecules、organisms は、基本的な化学の知識があれば理解できる階層を含意する。
- 一方で、名前を付けるのは難しく、不完全である。
  選んだ名前が自分や組織に合わなくても、まったく問題ない。
- GE のデザインチームは、Atomic Design の分類を同僚に示したときに戸惑われ、組織で成功させるには分類をもっと親しみやすくする必要があると結論した。
  最終的な分類は Principles、Basics、Components、Templates、Features、Applications である。
- 組織に合う分類を定めれば、全員が atomic design の考え方に賛同し、一緒に効果的に作業できる。
- 「Atomic design」という流行語は、モジュール式の設計と開発の概念をまとめ、関係者の説得や同僚との会話の略語として役立つ。
  しかし、厳格な教義ではなく、選ぶ分類は、組織が効果的に意思疎通し、優れた UI のデザインシステムを作る助けになるべきである。

## すべての UI への適用

出典: Atomic design is for user interfaces

- Atomic design はウェブから生まれたが、ウェブに限らず、あらゆる UI に当てはまる。
  Microsoft Word、Keynote、Photoshop、銀行の ATM など、あらゆるソフトウェアの UI に使える。
- ネイティブのモバイルアプリ Instagram を例に分解している。
  - Atoms: いくつかのアイコン、文字レベルの要素、2 種類の画像（主な画像と利用者のアバター）。
  - Molecules: 下部のナビゲーションバーや、写真への「いいね」やコメントの操作バーなど、アイコンや文字、画像の単純な組み合わせ。
  - Organisms: 利用者の情報、時刻、写真、写真への操作、いいねの数や説明文を合わせた写真の organism。
    これは Instagram の体験の要で、利用者が作る写真の終わりのない流れの中で繰り返し積み重なる。
  - Templates: 部品がレイアウトの中で組み合わさる様子と、利用者の名前、アバター、写真、いいねの数、説明文などの動的な内容の骨格。
  - Pages: 実際の内容を流し込んだ最終的な製品で、土台のデザインシステムがまとまって機能する UI になることを確かめる。
- Atomic design は、CSS や JavaScript などのウェブ固有の技術へのアプローチと誤解されやすい。
  「atomic design has nothing to do with web-specific subjects like CSS or JavaScript architecture」と明言されている。
  第 1 章のモジュール化の流れ（CSS や JavaScript を含む）は好ましい動きだが、atomic design は、使う技術によらず UI のデザインシステムを作ることを扱う。

## 結論

出典: Atomic design in theory and in practice

- この章は、atoms、molecules、organisms、templates、pages が協力して、思慮深く意図的なインターフェースのデザインシステムを作る方法を示した。
- UI を原子的な要素に分解して見ることも、それらが組み合わさって最終的な UI になる過程を同時にたどることもできる。
- 内容とデザインの密接な関係と、そこに入る内容に合わせたデザインシステムを作れることを学んだ。
- Atomic design の言葉は、同僚とモジュール性を話すための略語になり、デザインシステムに必要な階層の感覚を与える。
- Atomic design は便利な方法論だが、本質的には UI を作るための mental model にすぎない。
  本の残りは、それを実現するための道具と進め方を扱う。
