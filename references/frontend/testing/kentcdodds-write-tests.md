# Kent C. Dodds: Write tests. Not too many. Mostly integration. 要約

Kent C. Dodds が 2019 年 7 月 13 日に公開したブログ記事「Write tests. Not too many. Mostly integration.」の要約である。
題名は、Guillermo Rauch が 2016 年 12 月にツイートした一文であり、記事はその一文を 3 つの部分に分けて説明する。
外部資料の要約であり、最終的な根拠は原典を参照すること。
要点は「テストは書く」「カバレッジ 100% を目標にして書きすぎない」「信頼を得やすい統合テストに最も力を注ぐ」の 3 つである。

## Write tests.（テストを書く）

出典: Write tests.

- ほとんどのプロジェクトで、自動テストを書くべきである。
  自分の時間を大事にするなら、なおさらである。
- 午前 2 時の電話で不具合を直すより、手元のテストで不具合を見つけるほうがよい。
- テストを書くと、実装には時間がかかるかもしれないが、保守では自分も他の人もほぼ確実に時間を節約できる。
- テストを書くときに考えるのは、プロジェクトに不具合がないという信頼をどれだけ得られるかである。
- TypeScript や ESLint のような静的型付けや lint のツールでも、かなりの信頼が得られる。
  ただし、型や lint ではビジネスロジックの不具合がないことは保証できない。
  そのため、強く型付けされた言語でもテストは必要である。

## Not too many.（多すぎない）

出典: Not too many.

- 管理者やチームがアプリケーションに 100% のコードカバレッジを課すことは、とても悪い考えである。
- カバレッジが 70% 程度（著者自身が「根拠のない数字」と断っている）を大きく超えると、テストの見返りは逓減する。
- 常に 100% を目指すと、テストの必要がないものまでテストすることになる。
  たとえばロジックがなく、不具合があっても ESLint や Flow で捕まえられるものである。
  このようなテストの保守は、自分とチームを遅くする。
- テスト環境で再現しにくい 1 行を通すために、実装の詳細をテストしてしまうこともある。
  実装の詳細のテストは、アプリケーションが動く信頼をあまり与えず、リファクタリングを遅くする。
  リファクタリングでテストを直す必要があるのは、ごくまれであるべきである。
- 著者のオープンソースのプロジェクトのほとんどは 100% のカバレッジである。
  理由は、再利用される小さなライブラリやツールが多く、壊れると利用する多くのプロジェクトに深刻な問題が出るためと、100% にしやすいためである。

## Mostly integration.（主に統合テスト）

出典: Mostly integration.

### テストの種類とピラミッド

- 自動テストでよく話題になる形は、単体テスト（Unit）、統合テスト（Integration）、E2E（End to End）の 3 つである。
  それぞれにトレードオフがある。
- テストピラミッドは、下から Unit、Integration、E2E の順に並ぶ。
  Martin Fowler のブログと Google Testing ブログの図を組み合わせたものである。
- 上へ行くほど、テストの作成と実行が遅くなり、実行と保守の時間や資源の費用が増える。
  そのためピラミッドは、単体テストにより多くの時間を使うことを示している。
- ピラミッドが示していないのは、上へ行くほど各テストが与える信頼の度合いが増えることである。
  E2E テストは単体テストより遅く高くつくが、アプリケーションが意図通りに動く信頼ははるかに大きい。

### Testing Trophy

- 道具が進歩し、Martin Fowler のピラミッドの前提は成り立ちにくくなった、と著者は述べる。
  そこで著者は「The Testing Trophy」を作った。
- Testing Trophy は、JavaScript アプリケーションのテストの種類ごとの投資対効果（return on investment）の目安である。
- 記事が引用するツイートでは、層を次のように分けている。
  - End to end（Cypress の例）
  - Integration と Unit（Jest の例）
  - Static（Flow と ESLint の例）
- 記事の本文は、層ごとの配分の数字を挙げていない。
  述べているのは、統合テストに最も力を注ぐべきだということである。

### 統合テストを中心にする理由

- コンポーネント `<A />` がコンポーネント `<B />` に props `c` と `d` を渡して描画していても、`<B />` が props `e` なしで壊れるなら意味がない。
- 部品が単独で動くことを確かめる単体テストが少しあってもよいが、部品が一緒に正しく動くことも確かめなければ役に立たない。
- 一緒に動くことをテストすれば、単独でのテストは不要になることが多い。
- 統合テストは、信頼と速さ・費用のトレードオフの均衡がよい。
  そのため、努力の大半（すべてではない）を統合テストに使うのがよい。

### 統合テストを増やすには

- 統合テストと単体テストの境目は、少しあいまいである。
- 統合テストを増やすために最も効果があるのは、モックを使いすぎないことである。
- モックにすると、テスト対象とモックにした部分の統合についての信頼がすべて失われる。
- 毎回のテストでメールを送ったりクレジットカードに課金したりはしたくないので、モックが避けられない場合もある。
  ただし、たいていはモックを避けられ、そのほうがよい。
- React では、浅い描画（shallow rendering）もこれに含まれる。

## 結論

出典: Conclusion

- ソフトウェアのテストが時間の無駄だと主張する人はいないだろう、と著者は述べる。
- 最大の課題は、何をどうテストするかを知ることである。
  実装の詳細のテストによる偽りの信頼ではなく、本当の信頼を与えるテストにする。
