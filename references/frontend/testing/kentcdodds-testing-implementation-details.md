# Kent C. Dodds: Testing Implementation Details 要約

Kent C. Dodds のブログ記事「Testing Implementation Details」（2020 年 8 月 17 日）の要約である。
外部資料の要約であり、最終的な根拠は原典を参照すること。
要点は「実装の詳細をテストすると、リファクタリングで壊れる偽陰性と、壊れても通る偽陽性の両方が生まれる」「実装の詳細とは、コードの利用者が通常は使わず、見ず、知りもしないものである」「テストは利用者と同じ使い方をすべきである」の 3 つである。

## なぜ実装の詳細のテストは悪いのか

出典: Why is testing implementation details bad?

筆者は enzyme を使っていた頃、`shallow` による描画や `instance()`、`state()`、`find('ComponentName')` などの API を避けていた。
これらは、コンポーネントの実装の詳細をテストできてしまうためである。
実装の詳細をテストするテストには、次の 2 つの問題がある。

1. アプリケーションのコードをリファクタリングすると壊れうる（偽陰性）。
1. アプリケーションのコードを壊しても失敗しないことがある（偽陽性）。

テストの問いは「ソフトウェアは動くか」である。
テストが通れば「陽性」（動くソフトウェアを見つけた）、失敗すれば「陰性」（見つけなかった）である。
「偽」は結果が誤りだった場合を指す。
ソフトウェアが壊れているのにテストが通るのが偽陽性、動いているのにテストが失敗するのが偽陰性である。

記事では、`openIndex` という state を持つクラスコンポーネントのアコーディオンを例にしている。
実装の詳細をテストする例として、enzyme で次の 2 つのテストを挙げている。

- `wrapper.state('openIndex')` を調べ、`wrapper.instance().setOpenIndex(1)` を直接呼ぶテスト。
- `find('AccordionContents')` で子コンポーネントを探し、その Props を調べるテスト。

## リファクタリングでの偽陰性

出典: False negatives when refactoring

テストを嫌う理由として多いのは、テストの面倒を見るのに時間をかけすぎることである。
「コードを変えるたびにテストが壊れる」という不満が、その典型である。

複数の項目を同時に開けるようにする準備として、state を `openIndex` から `openIndexes`（配列）に変える場面を考える。
これは振る舞いを変えないリファクタリングであり、アプリでの確認でも問題なく動く。
しかし `setOpenIndex sets the open index state properly` のテストは、`openIndex` が `undefined` になって失敗する。

この失敗は本当の問題の警告ではなく、コンポーネントは正しく動いている。
これが偽陰性であり、壊れているのはアプリのコードではなくテストである。
筆者は、これ以上に腹立たしいテスト失敗の状況は思いつかないと述べている。

テストを新しい state 名に合わせて直すこともできるが、これでは同じ問題が繰り返される。
要点は、実装の詳細をテストすると、リファクタリングで偽陰性が起き、少しコードに触れただけで壊れる脆くて煩わしいテストになることである。

## 偽陽性

出典: False positives

同僚が、ボタンの `onClick={() => this.setOpenIndex(index)}` を、性能上の理由で `onClick={this.setOpenIndex}` に書き換えたとする。
`setOpenIndex` に `index` が渡らなくなるが、既存のテストはどちらも通る。
state の変化と `setOpenIndex` の呼び出しはテストされていても、ボタンが `setOpenIndex` に正しくつながっているかを確かめるテストがないためである。
テストが通ったのでブラウザで確認せずにコミットされ、本番でアコーディオンが壊れる。
記事は、これを Nancy がチケットを買えなくなる話として描いている。

これが偽陽性であり、失敗するはずのテストが失敗しなかった状況である。
対策として、ボタンのクリックで state が更新されるテストを足す、コードカバレッジの基準を 100% にする、実装の詳細をテストさせる API の使用を防ぐ ESLint プラグインを書く、といった手もある。
しかし筆者は、そのどれもやる気はなく、偽陽性と偽陰性にうんざりして、いっそテストを書きたくないとさえ思うと述べている。
そこで、うまくいく道が広い（wider pit of success）ツールがあればよいと述べ、そのツールはすでにあると続ける。

## 実装の詳細を含まないテスト

出典: Implementation detail free testing

enzyme でも、実装の詳細を含まない API だけに限れば書き直せる。
しかし筆者は、実装の詳細を含めにくい React Testing Library を使う。

書き直したテストは 1 つで、次の流れで振る舞い全体を確認する。

1. `items` を Props に渡して `Accordion` を描画する。
1. 最初の項目の内容が表示され、2 つ目の内容が表示されていないことを確認する。
1. 2 つ目の項目のタイトルをクリックする。
1. 2 つ目の内容が表示され、最初の内容が表示されていないことを確認する。

このテストは、state の名前が `openIndex` でも `openIndexes` でも `tacosAreTasty` でも通る。
これで偽陰性がなくなる。
クリックハンドラのつなぎ方を間違えればテストは失敗するので、偽陽性もなくなる。
規則の一覧を覚える必要はなく、ツールを慣用的に使うだけで、アコーディオンが利用者の望みどおりに動く確信を得られるテストになる。

## 実装の詳細とは何か

出典: So... What are implementation details then?

筆者が考える最も簡単な定義は、次のとおりである。

> 実装の詳細とは、コードの利用者が通常は使わず、見ず、知りもしないものである。

まず「このコードの利用者は誰か」を決める必要がある。
React のコンポーネントには、通常 2 種類の利用者がいる。

- エンドユーザーは、描画されたボタンや内容を見て操作する。
- 開発者は、コンポーネントに Props を渡して描画する。

したがって、テストが見たり操作したりするのは、Props と描画結果だけであるべきとされる。
React Testing Library のテストはまさにそうしている。
Props つきで要素を描画し、利用者に表示される内容を問い合わせ、描画されたボタンをクリックする。

enzyme のテストは、`openIndex` という state にアクセスする。
どちらの利用者も、その名前や、値が単一の値か配列かを知らず、気にもしない。
`setOpenIndex` メソッドも同様である。
それでもテストはこの 2 つの実装の詳細を知っている。

エンドユーザーや開発者と違う使い方をすると、アプリのコードが考慮すべき第 3 の利用者としてテストが生まれる。
しかし、テストは誰も気にかけない利用者であり、テストのためのテストは無駄である。
自動テストは、本番の利用者に対してアプリのコードが動くことを確かめるべきである。

> テストがソフトウェアの使われ方に似ているほど、テストは確信を与えてくれる。

## フックの場合

出典: So, what about hooks

enzyme はフックの扱いに今も苦労している。
実装の詳細をテストしていると、実装の変更がテストに大きく響くためである。
クラスコンポーネントをフックを使う関数コンポーネントへ移行するとき、テストが壊れていないことの確認に役立たない。

React Testing Library はどちらの実装でも動く。
筆者は、これを「実装の詳細を含まず、リファクタリングに向いている」テストと呼んでいる。

## 結論: 何をテストするかの手順

出典: Conclusion

適切なツールを使うことは、実装の詳細を避ける第一歩である。
さらに、次の手順で何をテストするかを決めると、適切な心構えが身につき、自然と実装の詳細を避けられる。

1. テストのないコードのうち、壊れたらとても困る部分を考える（例: 購入手続き）。
1. それを 1 つか少数の単位に絞る（例: 「購入」ボタンを押すと、カートの中身を載せたリクエストが `/checkout` に送られる）。
1. そのコードの「利用者」が誰かを考える（例: 購入フォームを描画する開発者と、ボタンを押すエンドユーザー）。
1. その利用者が手作業で動作を確かめる手順を書き出す（例: カートにダミーデータを入れてフォームを描画し、購入ボタンを押し、モックした `/checkout` API が正しいデータで呼ばれたことを確かめ、成功を模した応答を返し、成功メッセージが表示されることを確かめる）。
1. その手順を自動テストにする。

記事は最後に、2 つ目の enzyme のテストで `AccordionContents` コンポーネントの名前を変えるとどうなるかを、読者への演習として挙げている。
